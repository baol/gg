# Architecture

Purpose: define system boundaries and behavior contracts.

## Layers

| Crate | Responsibility |
| --- | --- |
| `gg-engine` | Typed commands, incremental readers, filtering |
| `gg-git` | Repository discovery and object access through gitoxide |
| `git-good` | CLI, egui/eframe on wgpu, view state, workers |

Dependencies flow from shell to adapter to engine. Keep the engine independent of Git libraries, UI, and platform services. CLI and UI share commands. Add abstractions for concrete responsibilities.

## Runtime

Use safe Rust and propagate errors with operation, path, and retry. Preserve objects, refs, index, and working files while browsing. Keep native paths in APIs and exact object identities; use Unicode for editable paths and replacement characters for display text.

Run Git reads/indexing on workers, publish immutable batches, and repaint for visible changes. Retain displayed results through loading and errors, labeled with their repository identity. Track requested and displayed repositories separately.

## Launch

Resolve the repository from cwd, including nested directories, or an explicit path. Interactive launch loads history immediately; the toolbar supports repository changes. CLI history streams JSON; failures use stderr and nonzero status. Represent bare repositories, worktrees, unborn branches, detached HEAD, and shallow boundaries explicitly.

## History sessions

Pin each session to repository identity and resolved HEAD. Carry generations through requests/results; apply current results. Refresh creates a replacement session, adopted when ready and interaction permits. Repository switches clear the old filter/selection; refresh preserves matching selection by ID, otherwise the first visible result.

Traverse the deduplicated union of commits reachable from HEAD and every local branch, remote branch, and tag. A single tip uses the incremental frontier: emit the newest committer timestamp, break ties by descending object ID, then enqueue parents. Divergent non-shallow tips use topological order so parents follow all children. Repositories with more than 512 divergent tips delegate that topological ordering to `git rev-list --topo-order --stdin` and read metadata through gitoxide; smaller graphs keep the in-process topo builder. The refs snapshot is reused so a large multi-ref repository is not scanned twice. Assign stable ordinals and retain continuation state; shallow traversal stops at recorded boundaries. Every reachable commit remains accessible.

Prioritize visible rows, overscan, then indexing/counting. Publish summaries, selected details, progress, completion, and errors. Summaries carry ID, subject, author, and date; selected details include full message and parents.

### Storage and budgets

| Resource | Contract |
| --- | --- |
| Traversal slice | At most 32 commits or 4 ms; foreground work between slices |
| Requests/responses | One coalesced slot each |
| Response page | Up to 256 summaries; cache the current worker page |
| UI cache | At most 768 rows and one selected full message |
| Session files | Commit records, fixed-size ordinal offsets, separate filter offsets; close with session |
| Graph state | Frontier/visited IDs scale with graph size; release visited IDs on completion |

Reuse records across viewport and filter requests. Retain rows and mark counts incomplete after storage/traversal errors.

### Count and interaction

Publish discovered count, optional approximate estimate, and completion. Use valid count information as a hint; otherwise show the growing discovered extent. Counting shares the ordered history index and ends with an exact total.

Anchor by commit ID and pixel offset. Preserve that anchor as the range grows. Freeze scrollbar geometry during scrolling, momentum, dragging, and scrollbar hover; preserve the thumb's grab offset. Apply pending extents after settling. Deep jumps show fixed-height loading slots and traversal progress.

Pin hovered content and hit targets until pointer leave. Bind press/release to the same commit. Fill off-pointer slots in place; make a hovered loading slot clickable after leave/re-entry. Preserve row identity, position, focus, and selection.

Queue reordering, session replacement, and filter-result replacement during hover or interaction. Release queued changes after the relevant interaction ends; a configurable quiet interval handles scroll settling, while pointer leave releases hovered targets. Scrolling may reveal/fill slots with stable geometry.

### Filtering

Each edit increments a revision, including repeated text. Preserve edits during opening/refresh and apply matching revisions. Search full messages progressively in traversal order; distinguish partial, complete, and empty results.

Preserve matching selection; otherwise select the first published match. Clear selection/details at zero matches. Apply result and selection changes together at an interaction-safe boundary. External changes produce a refresh indication; explicit refresh adopts them. Implementation gaps: [regression inventory](regression.md#remaining-coverage).

## Browser state and keyboard

| Action | Binding |
| --- | --- |
| Filter / refresh / copy full ID | Ctrl+F/R/C; Command on macOS |
| Previous / next commit | Up/Down, k/j, Ctrl+P/N |
| Previous / next page | Page Up/Down; Alt+V for previous |
| Open selected commit/file / return | Enter or Right / Escape, Left, or Back |
| Toggle commit details | Space |
| Selected commit actions | Alt+A or **Actions** in the commit inspector |

Emacs bindings use physical Control. Ctrl+V retains native paste. Escape leaves filter focus. Text editors and open menus retain editing/navigation shortcuts; focused buttons allow list navigation. Reading views use Up/Down, j/k, Ctrl+P/N, and page keys to scroll their content. Enter opens a full-width diff from either file-list layout. History bindings apply while history is visible and editors are unfocused. Empty results keep selection empty. The status hint keeps the core bindings readable at narrow widths instead of clipping; the Help window lists the full set.

The **Actions** menu in the commit inspector, the commit-row context menu, and the Alt+A route draw the **Commit** menu's own entries from the one command table (same labels, shortcuts, and disabled reasons), followed by **Copy subject**, **Signature details…**, and **Recovery…**. Right-clicking a row selects it first, because the Commit menu acts on the selected commit. At wide widths the selected commit is shown in a 58 px **commit inspector** under the history list (the History mockup): avatar, subject (13.5 px, full message on hover), the 8-character ID in a pill (click copies the full ID), **Review** (`Enter`) and **Actions** (`Alt+A`), and a second line with author, date, and parent(s). View › Commit inspector (`Space`) shows or hides it; the refs sidebar keeps the full height. Below 1040 px the details overlay (with **Commit actions**) is kept; Alt+A opens the corresponding details surface first when needed and then the same popup. The **Help** menu opens a concise keyboard-shortcut window. The visible control, the context menu, and the shortcut invoke the same command for the same target, readiness reason, and confirmation.

Opening a commit or comparison from History or Details records a return location with the exact selected commit ID, filter query, and pixel offset, plus whether the narrow Details overlay was the caller. Closing Review restores that location once. Review presentation changes do not add return locations or Back steps. Recovery records its source, the Reflog reference filter when present, and the source-specific selected entry; closing Review returns to that Recovery entry and filter, not to History.

One operation area sits directly beneath the toolbar, always present at a fixed two-line height so starting or finishing work never moves the panes below; when idle it summarizes the current branch, tracking, local changes, and stashes. It owns the running phase, progress, cancellation, and supported continuation controls across every view: operation-worker work, rewrite and history refresh, network progress with **Cancel**, branch work, and an in-progress merge, rebase, cherry-pick, or revert with **Resolve conflicts…**, **Continue**, **Skip**, and **Abort** as Git supports them. Merge has no **Skip**; stash-conflict recovery has no sequencer controls. Continue stays disabled while unmerged paths remain. Configuration closes on accepted submission, so a running rewrite does not block browsing; its area reports **Rewriting commits** and then **Refreshing history** until the replacement generation is accepted. Duplicate submission is refused and incompatible mutations stay disabled. The area is the only place for these controls; dialogs, the toolbar, and the status line do not repeat them.

Operation outcomes carry a severity, a concise summary, optional full details, and at most one recovery action. The status line keeps a fixed-height summary and exposes **Details…** when full text exists and a recovery button when one applies, such as **Resolve conflicts…**, **Recovery…**, **Retry push**, **Retry fetch**, or **Stashes…**. A warning that retains intent also offers **Dismiss**, which clears the intent without executing it. While the operation area is active, the status line yields to it and does not duplicate progress or recovery controls; after completion it reports the outcome again. Merge, rebase, recovery, rewrite, push, fetch, and stash results populate the same outcome shape; errors outrank success notices, and a remaining conflict or failed worker keeps its own visible surface. The details window keeps selectable, copyable full text.

Follow [bounded-reveal rules](design.md). Page by the rendered viewport with one row of overlap, clamp at history boundaries, and stream uncached destinations. Show cached selected metadata immediately; reserve the full-message slot while loading. Narrow details preserve hidden history selection and pixel offset.

Rationale: one bounded reveal preserves spatial context; overlapping pages retain reading context; fixed details slots keep loading visually stable.

## Presentation

Apply [design guidelines](design.md). Dialogs that ask for a decision or start a change (create, delete, merge, rebase, track, reset, stash, restore, drop, clone, force push, worktree and submodule changes, LFS fetch, export, base folders) and **Preferences** are modal: they sit above a dimmed backdrop that absorbs clicks and drags, and History, reader, and list navigation keys stay with the dialog until it closes. Tool and information windows (Stashes, Recovery, Worktrees, details, Keyboard shortcuts) stay non-modal so browsing continues beside them. **Automatic refresh.** There is no Refresh command. A file watcher (the `notify` crate: inotify, FSEvents, or ReadDirectoryChanges) watches the worktree and the Git directories. Changes are sorted into working files, the index, and refs or operation state (HEAD, refs, `packed-refs`, merge, rebase, cherry-pick, and revert state); objects, logs, and lock files are ignored. After 300 ms without events, a ref or operation change reloads the history (unless a load already started after the change) and the worktree status; other changes re-read the status and the frame summary. Before any menu, toolbar, search, or shortcut command runs, unsettled changes are applied at once and the operation state is re-read. Refreshes keep the previous content in place until the new content arrives. `Ctrl+R` is **Reword…** and `Del` (in History, with no popup open) is **Delete…**.

The OS window title reads `gg — ~/path` (the home folder shortened to `~`), followed by ` — rebasing <branch> · step <n> of <total>` or ` — rebase conflict · step <n> of <total>` while a rebase is stopped. Use a menu header, one stable toolbar beneath it, one operation area when work is active, a history column header, and fixed-height status line. Reserve counts/progress/errors. Show full paths on hover and edit paths explicitly. The 26 px menu bar (an egui menu bar: frameless titles, hovering moves between open menus) holds **Repository**, **Branch**, **Commit**, **Changes**, **View**, and **Help**, followed by the repository identity; on macOS a **gg** menu comes first with **Settings…** (`Cmd+,`) and **Quit**, otherwise **Repository** ends with **Preferences…** (`Ctrl+,`) and **Quit**. **View** lists Local Changes (`Ctrl+1`), History (`Ctrl+2`), Commit details (`Space`), and Refs sidebar (`Ctrl+\`). The logo sits at the start of the toolbar; each command has one menu home as listed in the [final design](final-design.md#command-placement). The toolbar keeps, left to right and in the same place in every view and at every width: the refs sidebar toggle, the **Changes** tab (Local Changes, with a badge counting changed paths when there are any) before **History**, then Phosphor icon buttons for Fetch, Pull (rebase), Push, New branch, New tag, Merge into current, Stash changes, the Stashes picker, Interactive rebase of this branch, and Recovery. Each icon button has a tooltip naming its command and its menu shortcut (for example `Fetch  Ctrl+Shift+F`) and shares its menu item's enablement and disabled reason. Pull is enabled only when the current branch has an upstream and is behind it, and badges the behind count. A background read on load, on Local Changes refresh, and when the window regains focus records the number of changed paths (staged, unstaged, untracked, or conflicted, each path once), the stash entries, and the current branch's own commits; it never blocks a frame. **Stash changes** is disabled with *No local changes to stash* on a clean worktree. The **Stashes** button shows the entry count and a caret and opens a 440 px picker listing each entry in two-line, 40 px rows, as in the mockup: the ref on the left, the message (without the `WIP on <branch>:` prefix) over `on <branch> · <age> · <n files>` (**detached** when there is no branch) (changed paths against the commit the stash was made on, plus untracked files it stores; counted for the newest 50 entries by the background summary, never on the UI thread). The picker has a fixed size: the list scrolls in six rows and the action area reserves room for the drop confirmation and an error (the refs sidebar's **Stashes** group lists the same entries, follows the refs filter, and opens the picker on the chosen entry); Up/Down select an entry, Enter applies it (or confirms a pending drop), Del asks to drop it, and Esc cancels the drop question; the header names these keys (`Up/Down choose · Enter apply · Del drop`); **Drop…** sits apart at the right, in the error color. the selected entry offers **Apply**, **Pop**, **Show changes** (the stash commit in the ordinary review, returning to the caller), and **Drop…** with an inline confirmation. The toolbar rewrite covers the current branch's own commits, independent of the history selection: the commits its upstream lacks, or, when everything is pushed or there is no upstream, the commits the default branch lacks. It is disabled with a reason when the branch has none; **Commit → Interactive rebase from here…** keeps rewriting from the selected commit. Ref browsing remains reachable through the Branch menu and the wide refs sidebar. The toolbar ends with the current-branch button and a right-aligned search field, whose placeholder reads *Search commits, branches, files, actions* with a `Ctrl+K` chip when there is room (*Search* when space is short); when the window is too narrow, the branch button shrinks to an icon and the field to a search icon. The current-branch button names the checked-out branch (or detached HEAD) with its ahead/behind counts and opens a switcher: a filter field (every word must match), the local branches with the current one first, marked, and disabled, and **New branch from HEAD…**. Choosing a branch requests the ordinary validated switch, so the clean-worktree check and blocked-switch intent still apply. `Ctrl+K` focuses the field and typing opens the results under it (narrow windows: the icon opens the same results with their own field); `Ctrl+K` again, `Esc`, or a click outside closes it and clears the text. The results keep one fixed height whatever matches. Its results are grouped: **Filter** (filter History by the text; first and preselected), **Actions** (every toolbar and menu command named with its menu home, disabled with the same reason as its menu item), **Branches**, **Remotes**, and **Tags** (inspect the ref's commit, never moving HEAD), and **Files** (tracked paths read in the background summary, at most 50,000; choosing one opens the latest commit that changed it in Review with that file selected), at most eight per group. Every word of the query must occur in a result's label or context, ignoring case; labels that start with the query come first. Up/Down choose, Enter or a click runs the result through the same command dispatch as the toolbar, and running closes the popup. `Ctrl/Cmd+F` opens the same search starting from the current History filter (its first result applies it). There is no filter row: the History column header reads `Commit · <count>` (`+` while counting) and shows the active filter as a chip with a clear button.

History columns: dot, subject, author image/name, short hash, date. Preserve minimum table width with horizontal scrolling. Use high-contrast selection. Group details portrait, author/date, subject, and copyable IDs; retain full IDs behind abbreviations.

Below 1040 logical pixels, details replace history reversibly; wider windows use a resizable side pane preserving table width.

### Avatars

Use a bounded Gravatar worker keyed by normalized email SHA-256. Cache one validated 128-pixel image per author; display at 18 pixels in history and 64 in details, with reserved initials fallbacks. Retain one decoded source and at most two display-sized textures per cached author; filter thumbnails for the current display scale.

Persist images and 404 results in the OS cache. Read disk first; deduplicate author requests across texture eviction. Attempt transient failures once per session; retry next launch. Replace corrupt entries atomically. Bound bytes, decoded dimensions, timeouts, queues, and GPU cache. Publish/evict images after history/details hover and scrolling end. Cache location: [development](development.md).

## Commit review · M1 specification

### Comparison

Pin repository, commit, and parent IDs. Resolve revisions once. Default to first parent; roots compare with the empty tree. List merge parents in stored order with one-based numbers, short IDs, and full-ID tooltips. Parent changes reuse the pinned commit ID. Missing parent objects produce an identified incomplete-comparison state; retain metadata during loading/errors.

Keep exact Git path bytes and a one-line display string. Preserve Unicode; escape backslashes, controls, and invalid bytes (`\xNN`) so distinct paths have distinct labels. Copy Unicode paths verbatim; label the fallback **Copy escaped path**. CLI `--file` matches native path bytes. Changes carry old/new object IDs and modes, with added/deleted/modified/type-changed status. CLI and UI share deterministic Git tree traversal order. Represent moves as deletion/addition in M1, retaining both sides for future rename detection.

Parent switches retain the displayed comparison through loading/failure, label its identity, and offer retry. Adopt replacement files and diff together after pointer leave and scroll settling. Start the new comparison at its first file; empty comparisons clear selection. Independent worker mailboxes isolate superseded requests.

### Loading

Stream file summaries before blob reads. Virtualize rows using history's paging and interaction rules; counts progress to exact completion. Within a comparison, preserve selection by exact path, otherwise first result; clear it for empty comparisons.

Keep requested and displayed file identities separate. Retain the displayed diff and its scroll offset while a replacement loads; publish its identity, metadata, preview, and rows together after hover and scrolling settle. An explicit new file selection is the exception: it publishes once even when the resting pointer is already over the reader, so narrow layouts that replace the file list with the reader do not wait forever. Asynchronous page replacements still wait for hover to clear. Errors retain labeled previous content. Reset the new file to its first row on adoption.

Panes never show loading text ([design rule](design.md)). History, Review, Local Changes, and diff rows that are not read yet keep their fixed slots empty; the commit details message slot stays empty until the message arrives; an empty Review file list stays blank until its first files arrive (only a finished empty comparison says so); a reader with no content yet, an unread full file, and a file-history reader before its first page stay empty; and the Worktrees, submodule, and LFS windows stay empty during their first read, showing progress only for changes they make (adding or removing a worktree, updating a submodule, fetching an LFS object). The reader's one-line state slot is always reserved and carries only completeness notes and errors, never loading. Endpoint labels show the reference alone (`HEAD`) until its commit is known. Progress for long reads belongs in the status line and the operation area.

Read selected-file content on a worker independent of history indexing. Key results by review generation, comparison, and file. Coalesce requests, cancel obsolete work between batches, and apply current results. Page diff rows and keep every file reachable through bounded caches.

### Changed-file implementation

Walk trees depth-first in Git tree order, skip identical subtrees, and defer blob contents to selected-file requests. The frontier scales with active tree entries. Yield between tree visits; individual tree decoding remains one operation.

Use an independent comparison worker with 32-step/4-ms slices, one request/result slot, temporary record/offset files, 256-row pages, and at most 768 UI rows. Retry replaces the worker and its mailbox for the same pinned comparison, retaining selected path, displayed diff, pixel anchor, and known count while enumeration catches up. Immutable comparison IDs preserve path order. Closing review cancels it; obsolete mailboxes remain isolated.

A line counter runs beside the comparison worker on the same record file and counts added and deleted lines per file like `git diff --numstat`: requested rows first, then every listed file in order, in 8-ms slices. It reads object headers before content and counts only within the text-diff budgets (2 MiB per side, 100,000 combined lines, the 250-ms algorithm deadline); binary content is marked `bin`, while gitlinks, over-budget sides, and unreadable objects stay uncounted. A file/symlink type change counts every line of both sides, as Git splits it into a deletion and an addition. Its mailbox publishes the requested rows' counts and the running total, complete once the listing finished and every listed file is counted; counts wait while a replacement comparison is pending, and a retried comparison keeps its finished total.

Present status/path rows and selected before/after IDs and modes. A persistent Before/After header names the resolved base and target commits; when the comparison is against a ref such as `HEAD`, the ref name is shown with the resolved commit. The commit-row action is **Compare with current HEAD**. The commit identity strip names the selected commit subject only; the shared reader names the selected path and exact endpoints once, so the path and endpoint labels are not repeated above it. Wide layouts show a fixed 300 px file list at the left and the reader in the remaining width; narrow layouts open a separate reading view with ‹ Files. History state and incoming history results wait while review is open; Back restores its caller location and pixel offset before applying current results.

### Diff and layout

Use one selected-file worker with one coalesced request/result slot. Retain one bounded document on the worker; publish at most 256 rows per page and cache at most 768 UI rows. Check blob headers before allocating content. Compare up to 2 MiB per side and 100,000 combined source lines with a 250-ms algorithm deadline. Return an explicit incomplete summary when a budget is exceeded. Cancel before each object header/content read and during row projection; object decoding and the deadline-bound algorithm finish their current operation. Reuse the document for viewport requests.

Use unified diffs with old/new line numbers, fixed-height rows, the window's context lines (3, 5, or 10; default 3, like `git diff -U<n>`), and missing-final-newline markers. The window's whitespace option compares lines by all bytes (default), without whitespace before the line end (`--ignore-space-at-eol`), or without any whitespace (`-w`); rows keep exact bytes, unchanged lines show the new side as Git does, and a file whose only differences are hidden says *Only whitespace changed; whitespace changes are hidden*. The options travel with each diff request; changing them reads the open comparison again as a new generation, centered on the current line. Label byte sizes Before and After. Preserve whitespace/line endings. With **Show invisible characters on changed lines** (default on), added and removed lines draw each tab as `→` and each trailing space as `·` in the weak text color; every marker takes the place of one displayed space, so columns and widths do not move, and context lines and Full file stay plain. Scroll long source lines horizontally in an explicit reading view; with **Wrap long lines** (default off) Diff (both layouts) and Full file instead continue a long line on extra rows of the same fixed height, with the gutter (line numbers, sign, pick box, blame) only on its first row and no sideways scrolling. Text breaks at the last whole monospace column of the reading area, not at word boundaries (`wrap_rows::Wrap` maps display rows to source rows by binary search), so row positions come from character counts the diff worker publishes for every row and virtualization, paging, change navigation, and line picking keep working before rows load. Working comparisons always reserve the pick column while wrapping, so picking never reflows text; resizing the window or switching layout, presentation, or side measures again and keeps the top row in view. Characters wider than a monospace column (such as CJK) can be clipped at the right edge of a wrapped row. Distinguish context/additions/deletions with symbols and color.

| Content | Presentation |
| --- | --- |
| Binary blob | Before/after PNG/JPEG image previews; hexadecimal fallback; IDs and byte sizes |
| Symlink | Labeled target text, read directly from the blob |
| Gitlink | Referenced commit IDs, including unavailable submodule objects |
| Mode-only change | Metadata summary with before/after modes and unchanged content; read object headers only |
| Undecodable bytes | Escaped display; exact comparison bytes |
| Size/computation limit | Explicit summary, completion state, exact-side export |

Review opens a file-list/diff workspace. One header line holds Back, the short commit ID and subject (truncated, full text on hover), Prev/Next file while reading, History, and parent selection. The file list starts with a `FILES n` header (`n+` while listing) and the green/red `+x −y` line totals at its right, each number followed by `+` until every file is counted. Each row shows the change symbol, the path elided at its start (`…/folder/file.rs`, the full path and change kind on hover), and the file's line counts (`+18 −7`; zero sides left out, `12k` past 9,999, `bin` for binary) right-aligned in a fixed slot as wide as `+9999 −9999`, so rows never move when counts arrive; uncounted files leave the slot empty. Narrow windows show files and content successively. Back restores the recorded caller location: history selection, filter, and pixel anchor for History or Details callers. Shortcuts belong to the active context; editors retain theirs.

### Binary previews and export

Decode PNG/JPEG on the selected-file worker. Bound each side to 16 MiB encoded, 8 megapixels, 4096 pixels per dimension, and 64 MiB decoder allocation. Fit previews to 1024 pixels; show original dimensions. Unknown, corrupt, and oversized images retain a labeled hexadecimal preview of the first 256 bytes when inside the encoded budget. Larger blobs retain summaries and export. Publish current-generation previews at the diff's interaction-safe boundary; retain one preview pair and two textures.

Image comparison names each side's short blob ID, exact dimensions, encoded bytes, and absent, gitlink, binary, or budget state. Wide layouts offer **Side by side** and **Swipe**; narrow layouts stack named Before/After previews. **Fit** preserves each image's aspect ratio and never upscales; **Actual size** shows 100% with scrolling and a visible zoom label. Swipe aligns each image by its own dimensions without stretching, clips the After image at a labeled boundary slider that also responds to keyboard arrows, and permits dragging the boundary on the canvas. A theme-aware checkerboard behind both previews exposes transparency. Export remains per side and preserves the complete original bytes.

**Onion skin** is the third wide presentation: Before is drawn full and After is overlaid at an explicit opacity, initially 50%, with a labeled opacity slider that is keyboard-adjustable when focused. It preserves Fit/Actual size, per-side dimensions and byte metadata, checkerboard transparency, and per-side export, requires both images, and centers each at its own size without stretching. When either side is absent, the presentation states that both images are required and keeps the explicit per-side absence state instead of blending. Normal alpha blending is the only mode; difference heatmaps and other blend modes remain separate work.

Export either present blob side to a new user-chosen path, preserving exact bytes. Write a temporary file beside the destination, then publish without overwriting. Keep Git metadata outside export destinations. Export symlink target bytes; gitlinks retain referenced commit IDs. Cancel before object decoding and between 64-KiB writes; remove temporary output on cancellation/failure. Run one export per review view, pin its path/object identity, and cancel on closing the export or review. Escape closes the export window before review navigation resumes. Gitoxide decoding uses memory proportional to the selected object and delta chain; output writes use fixed-size chunks.

### CLI

`git good show <commit> [--repo PATH] [--parent N]` streams JSON summaries. Add `--file PATH` for a repository-relative selected-file diff, including exact source-line bytes. Add `--export before|after --output PATH` to save that side and emit a JSON receipt. Use cwd discovery by default. Validate one-based parent numbers; roots use the empty tree automatically. Include repository/comparison identity and exact path bytes. Apply runtime error conventions; document usage when implemented.

Rationale: summaries provide early feedback; pinned, cancellable work keeps rapid selection accurate; a dedicated review view gives source readable width.

## History graph and refs · M3

Ref discovery is read-only and shared by CLI and native views. Emit HEAD state (symbolic name, detached flag, commit), local branches, remote branches, and tags with exact short and full names and peeled commit IDs. Skip symbolic remote `HEAD` refs and tags that cannot peel to commits. Keep HEAD explicit for unborn and detached repositories. `git good refs [PATH]` streams this snapshot as JSON; the history worker loads the same snapshot alongside a traversal and replaces it on refresh. History traversal starts from HEAD and every ref target, so branch, remote, and tag-only commits appear in the graph.

Compute graph rows in traversal order, including commits later hidden by a filter, so lane identities stay coherent. Each row carries its own lane, the set of lanes entering and leaving the row, and parent lanes. Reuse a parent's existing lane, allocate free lanes for additional merge parents, retire empty lanes, and cap layout at 64 lanes. Render stable per-lane colors, vertical continuations, parent joins, commit dots, and a ring for merge commits. A single-parent branch keeps its own lane color until it joins an existing lane; merge parents always use the parent lane color. Only the row's own lane starts a downward segment at the commit; newly created parent lanes are connected by their joins. Cache graph rows with the visible page and evict them with their commits.

Render matching refs as pills before the subject, with tags first, then local branches (the current branch first), then remotes, as in the History mockup; in the dark theme tags are gold and branches blue. Show up to four pills when the subject column has room (two when it is narrow) plus an explicit overflow count. Include the ref-kind icon in each pill and keep long labels single-line. Clicking any pill selects its target commit for inspection without moving HEAD. Ref selection never switches branches or creates tracking branches.

At every width, keep **Local Changes** and **History** in the toolbar row directly beneath the menus, in that order and at the same position. The wide layout additionally shows a user-resizable left refs sidebar with the refs filter and collapsible groups headed in small caps with their count (`BRANCHES 2`, `REMOTES 5`, `TAGS 19`, `STASHES n`; branch rows with an upstream end with their dimmed ahead/behind counts (`↑1 ↓3`, zeros left out), plus `WORKTREES n` when the repository has linked worktrees, listing each folder with its branch, the open one checked, another opening on click; Remotes, Tags, and Worktrees start collapsed, and every group opens while the filter has text; new branches and tags come from the toolbar and Branch menu), slash-separated folder nodes, HEAD checkmark, and branch/remote/tag icons. The selected branch is bold; its branch glyph uses the same deterministic ref color as its history graph lane, with a same-color dot behind the glyph. Below the sidebar breakpoint, the Branch menu provides the same ref browsing and the toolbar's sidebar toggle is disabled with a reason. The same sidebar and toolbar stay visible while Local Changes is open; the main content area switches between the history table and the Local Changes workspace. Clicking any sidebar row, Branch menu ref item, or graph pill inspects its target commit. A branch double-click requests the same validated switch as **Switch to <branch>**; it switches only if the operation is safe and undoable, otherwise preserves the target and offers the existing explicit recovery intent. The current branch remains a no-op. Selecting a ref clears a hiding filter, targets its commit by ID, and scans the completed spool to recover the row before revealing it. Ref navigation never moves HEAD, checks out content, writes refs, or modifies the index or working tree unless the explicit switch gesture is used.

### Branch switching and creation

Switch and create operate on local branches only after a clean-worktree check. Open the observed status identity, scan for staged, unstaged, or conflicted paths, and reject the action before invoking Git if any tracked change is present. Untracked files do not block switching or creation; Git still refuses a checkout that would overwrite them, and that failure is reported without deleting user files. ## History mutations and recovery · M5

### Stash

A reference is accepted only as `stash@{n}` or a bare `n`; option-shaped or non-numeric references are rejected before Git runs.

Push records modified and staged changes, optionally including untracked files and keeping staged content in the index. In the app, **Include untracked files** starts checked ("stash my changes" usually means new files too) and then remembers the last submitted choice; the CLI keeps Git's default and includes them only with `--include-untracked`. A clean worktree is an actionable error, not an empty receipt. Apply and pop restore the selected entry; `--index` also restores staged state. When Git reports conflicts, the operation keeps the stash entry, lists the unmerged paths, and leaves the conflict markers in the worktree. Pop removes the entry only after a conflict-free apply. Drop removes the selected entry after an explicit confirmation and never touches working files.

`git good stash list [--repo PATH]` prints a JSON snapshot with the repository and entries. `git good stash push [-m MESSAGE] [--include-untracked] [--keep-index] [--repo PATH]`, `git good stash apply|pop [STASH] [--index] [--repo PATH]`, and `git good stash drop [STASH] [--repo PATH]` print JSON receipts with the reference, applied/created/dropped state, conflicts, and warnings. The native **Changes → Stash changes…** dialog (also on the toolbar) records a message and the untracked/keep-index options. The **Stashes** window lists entries with exact references and offers one **Restore…** form plus a separate confirmed **Drop**. The restore form exposes **Restore staged state** and **Remove stash after successful restore**; remove maps to pop only after a conflict-free apply, and a failed restore keeps the form, entry, and inputs. Successful stash mutations refresh the history, refs, and status boundary so the worktree state stays current. A conflict reports its paths in the status line and keeps the entry for recovery; stash conflicts never grow sequencer controls.

### Merge, cherry-pick, revert, and recovery

Merge, cherry-pick, and revert are explicit mutations delegated to Git so commit order, parent selection, hooks, and conflict behavior match the executable. Each operation validates a clean worktree, resolves one explicit commit or ref, and reports conflicts with unmerged paths instead of manufacturing a result. An in-progress merge, cherry-pick, or revert is detected from the repository state and exposed as Continue, Skip where supported, and Abort. Abort restores the pre-operation HEAD, index, and worktree as far as Git can; failures report detail for manual recovery without deleting user files. Conflict resolution shows base, ours, and theirs content for each unmerged path and marks a path resolved by staging it.

**Resolve conflicts…** opens the conflict workspace in the main content area, under the operation area, in place of History, Local Changes, or Review; **Close** or `Esc` returns to that view. The workspace fills the content area and changes size only with the window: the paths list has a fixed width, the blocks, result, and side panes keep fixed heights, and an error or the empty state shares one reserved line. The conflict workflow names the operation, unresolved count, and operation commit above the content. It keeps Git's Ours/Theirs terms but explains what each side means for the operation, including rebase where Ours is the rewritten branch so far and Theirs is the replayed commit.

Text conflicts resolve **Block by block** by default. `gg_git::conflict::blocks` runs `git merge-file -p --diff3` on the file's stages (in a temporary directory, so neither the working file nor `merge.conflictStyle` changes the result) and `gg_engine::conflict::parse_diff3` splits the output into common text and blocks. Each block shows Base, Ours, and Theirs side by side (stacked when narrow, leading indentation kept) and takes **1 Ours**, **2 Theirs**, **3 Ours + theirs**, or **4 Theirs + ours**; keys 1–4 act on the current block (outlined; clicking a block makes it current) and move to the next block without a choice; `[` and `]` move to the previous or next block, wrapping. Each block header names the line where it starts in our version (`line 41`), and the block-by-block Result preview has line numbers. The files panel follows the conflict mockup: `CONFLICTED n` rows marked `!` (the selected file shows its blocks left, `2 left`), then `RESOLVED, STAGED n` with the files staged while the workspace was open, marked ✓. The workspace has no heading; the operation row holds **Close** (`Esc`). **Open in editor** (right of the Resolve modes) opens the selected working file with the editor command from Preferences › General › Editor (`{file}` is replaced by the path, which is otherwise added at the end; quotes group words), or with the system's default app (`xdg-open`, `open`, or `start`) when the command is empty. gg does not wait for the editor; the file watcher picks up the saved file. They wait only while a text field has focus. The **Result** preview composes the choices and keeps `<<<<<<< ours` / `||||||| base` / `=======` / `>>>>>>> theirs` markers for blocks without one; **Stage resolution** is enabled when every block has a choice and publishes the composed text through `publish_text`, which applies the same stage and working-byte revalidation as whole-file publication and keeps our side's executable bit. Binary, oversized, deleted-side, symlink, mode, and submodule conflicts have no blocks; **Block by block** is disabled with the reason and the **Whole file** sources below apply.

In **Whole file** mode, Base, Ours, Theirs, and the working file are preview sources: choosing one changes only the **Result** preview and never writes or stages anything. The working file is the default preview, so external edits are inspectable before publication. **Stage resolution** is the single publication step; it revalidates the conflict stage IDs and exact working bytes captured by the preview, then writes the chosen result and stages the path. A changed stage or working file returns an actionable stale-preview error in the conflict workspace and status line and requires **Refresh external edits**. If the worktree write succeeds but staging fails, the error states that the working file was already replaced; the review path, operation state, and index remain inspectable. Oversized regular working files are validated by exact streaming hash without a text preview; absent, symlink, directory, and submodule worktree paths keep Base/Ours/Theirs previews but disable a Working preview with an explicit reason. Stage resolution is disabled while another operation owns the area or the selected preview source has no content. Continue stays disabled while unmerged paths remain and explains why. Conflict listing, content reads, and resolution publication run on workers; after success the view selects the next unresolved path predictably. At wide widths the three side panes stay side by side with a bounded Result preview beneath them; at narrow widths Base/Ours/Theirs/Result are side tabs with one bounded scroll region, and the path list stays in its own bounded scroll.

Merge, rebase, and continue/skip/abort run on one background operation worker. The dialog closes immediately, the operation area names the running continuation, and duplicate or incompatible mutation actions stay disabled until the result arrives. Success refreshes mutation state, history, refs, status, reflog, and backups once; failure clears the pending label and reports the error while preserving Git's recovery state. UI mutations run on a worker, disable duplicate actions while pending, and refresh refs/history/status at an interaction-safe boundary.

## History rewrites and recovery · M6

### Amend

Amend rewrites the latest commit with the current index and an edited message. It requires an existing HEAD and a working tree, validates the repository status, pins the previous HEAD, and preserves the previous commit's author and parents. The committer identity and time come from the current configuration. An empty index is valid for a message-only amend; unlike a normal commit, the tree may equal the old tree.

Amend mode compares the index with the parent of HEAD rather than with HEAD. `StatusIdentity.base_tree` pins that parent tree (the empty tree for a root commit), and `Session::open_amend`, `working_diff`, and `unstage` use it as the before side. The staged rows therefore describe the proposed commit contents: existing changes in HEAD remain visible, newly staged working changes join them, and unstaging a file, hunk, or line restores the parent side in the index. Staging still compares the index with the working tree. Working files are never modified by staging or unstaging, and the usual index-lock, stale-observation, conflict, and whole-file mode checks apply.

Run `pre-commit`, `prepare-commit-msg` with the message file, `commit` source, and the old commit ID, then `commit-msg`. Re-read the message and index afterwards, reject a HEAD change made by a hook, acquire the index lock, rebuild the tree, and write the commit object with the original parents. Update `HEAD` atomically with the observed old ID as the expected value and write a `commit (amend): subject` reflog entry. Run `post-commit` and `post-rewrite amend` after publication; their failures are warnings because the rewrite already exists. `post-rewrite` receives the old and new IDs on stdin through `git hook run --to-stdin`, because the hook runner does not forward the parent process's stdin.

Before publication, create `refs/gg/backup/<label>/<unix-nanos>` pointing at the previous tip. A backup failure aborts the rewrite. Backup refs are private recovery anchors: the refs snapshot excludes `refs/gg/`, so they never appear in the sidebar or graph labels. The amend receipt carries `amended`, `previous`, and `backup` in addition to the commit, tree, parents, and warnings. CLI `git good commit --amend -m MESSAGE` prints the same receipt.

The Local Changes commit/amend form sits below the reader: at the lower right in wide layouts and below the reader at narrow widths, so it remains available while reading a comparison. It exposes an **Amend HEAD** toggle; the message field's placeholder reads *Commit message (first line is the subject)*, and the button's tooltip names its shortcut (`Ctrl+Enter`, or `Ctrl+Shift+Enter` when amending). The change groups are headed `UNSTAGED <n>` and `STAGED <n>`, with **Stage all** and **Unstage all** at the right of their headers (the same commands as the Changes menu). A hovered or selected row shows a **+** (stage) or **−** (unstage) button in a fixed slot at its right edge; conflicted and intent-to-add rows have none. With a list focused, `S` stages the selected Unstaged file and `U` unstages the selected Staged file. The status line follows its summary with the mockup's hints (`S / U: stage / unstage · [ ]: hunks · Ctrl+Enter: commit`); refresh is automatic, so the old Refresh button is gone and **Retry** appears in its slot only after an error. Review's file list shows `Esc: history · Up/Down: files · [ ]: changes · Alt+Left/Right: versions · H: file history · B: blame`. Unstage all is disabled while amending, because it resets the index to HEAD while Staged shows HEAD's parent. Enabling it loads the current HEAD message without replacing a nonempty amend draft, keeps the normal draft separate, restarts status against HEAD's parent, and shows a banner above the form that names the affected commit and subject, names the amend base (its parent or a root/empty tree), and explains that staged changes are the commit contents. The action becomes **Amend HEAD**; the same reader provides the header **Stage** and **Unstage** button, plus hunk and line stage/unstage actions on the active comparison. Unstage in amend mode removes the selected change from the amended commit and leaves working files unchanged. After success the toggle and amend base clear, the status line reads **Amended HEAD → \<id\> · N files**, the remaining normal draft is retained, and the lists refresh against the new HEAD.

### Reflog

Read reflog entries through `git reflog show --date=unix --format=%H%x00%gD%x00%gs REF`, with `HEAD` as the default. Parse the timestamp from the dated selector, reconstruct stable `REF@{n}` index selectors from entry order, and split the subject at the first colon into an action and detail. Missing refs, option-shaped references, and Git failures return actionable errors; listing is read-only and never changes refs, the index, or working files. `git good reflog [REF] [--repo PATH]` prints the repository, reference, and entries as JSON.

The native **Repository → Recovery…** window has one source selector for **Backups** and **Reflog** and keeps their distinct provenance, identifiers, and readers. Its default width and maximum resize stay inside the available viewport, including 720×480, with no clipped controls. Reflog defaults to `HEAD` with a selector for `HEAD` and local branches. Selecting an entry shows its full ID, relative time, action, and detail, with **Open commit**, **Reset branch here** (Soft, Mixed, or Hard), **Create branch here…**, and **Copy hash**. **Open commit** runs the ordinary commit review and records the recovery source, the Reflog reference filter, and the source-specific selected entry as its return location; Back returns there. Reset reuses the existing reset path and confirmation, including the Hard warning that staged and working changes are discarded. Create branch resolves the selected commit, validates the name, rejects an existing branch, and uses the shared form with **Switch after creation** off; the current branch and worktree stay put. Successful reset and branch creation refresh refs, history, status, and the open Recovery source.

### Rebase

`git good rebase REF [--autostash] [--repo PATH]` rebases the current branch onto one explicit local branch, remote-tracking ref, or tag. The reference is resolved to a commit before any mutation. A tracked working tree must be clean; `--autostash` is the explicit opt-in for working changes. The backend always passes `--autostash` or `--no-autostash`, so repository configuration cannot silently change the decision. Untracked files do not block the clean check; Git still refuses a rebase that would overwrite one. An operation already recorded by Git must be recovered before another rebase starts.

Before Git runs, pin the current HEAD and create `refs/gg/backup/rebase/<unix-nanos>` pointing at it. A backup failure aborts the rewrite. The rebase itself runs through Git with non-interactive editors so commit order, hook behavior, and conflict semantics match the executable. The receipt carries `reference`, resolved `commit`, `previous`, `backup`, `applied`, `in_progress`, `conflicts`, and `warnings`.

An in-progress rebase is detected through `rebase-merge` or `rebase-apply`, with the commit being applied read from `REBASE_HEAD`. The operation area names the rebase and exposes **Continue**, **Skip**, and **Abort**; the conflict window lists unmerged paths, and **Recovery…** remains in Repository and in the outcome recovery action. Continued and aborted rebases refresh history, refs, status, an open reflog, and open backups, and restore the pre-rewrite history row. `git good rebase --continue|--skip|--abort [--repo PATH]` prints the same receipt shape with null reference, commit, previous, and backup fields.

The native **Branch → Rebase current onto…** action and each branch, remote, and tag context menu open a confirmed **Rebase branch** dialog with a reference field and an **Automatically stash working changes** option. The dialog states that the rewrite creates a private backup ref. Ref actions are disabled while a mutation is in progress.

### Interactive rebase

`git good rewrite --from COMMIT [--autostash] STEP... [--repo PATH]` rewrites the linear range from the named commit through HEAD. A step is `--pick`, `--edit`, `--squash`, `--fixup`, or `--drop COMMIT`, or `--reword COMMIT MESSAGE`, in todo order (oldest first). The start commit is resolved and checked as a HEAD ancestor. The range is listed oldest first and must be linear; merge commits are rejected rather than flattened. Every range commit must appear exactly once in the ordered steps.

The engine plan (`gg_engine::rewrite::Step`) has six actions:

- **pick** keeps the commit.
- **reword** keeps the commit with the step's new message, stored as given apart from whitespace cleanup (`#` lines are kept). The message must not be empty, and only reword steps carry one.
- **edit** (shown as **Reopen**) picks the commit, then stops with its changes staged on its parent, so they can be committed again whole or in parts before **Continue**. The todo line is `pick` followed by an `exec` script that writes `<git-dir>/rebase-merge/gg-reopen` (the parent, then the original commit), runs `git reset --soft HEAD~1`, and exits non-zero so Git always stops there; `--no-reschedule-failed-exec` keeps Continue from running it again. A root commit has no parent, so it stays at HEAD to be amended. The receipt reports `in_progress` without conflicts and a warning naming the reopened commit.
- **squash** combines the commit into the nearest kept commit before it and joins both messages; **fixup** does the same and keeps only the older message. Both are refused when no kept (non-dropped) commit precedes them.
- **drop** leaves the commit out. Dropping every commit is refused with a pointer to Reset.

The CLI receipt carries `from`, `previous`, `backup`, `applied`, `in_progress`, `conflicts`, `warnings`, and the step count.

The backend writes the whole interactive-rebase todo to `<git-dir>/gg-rewrite/todo` and installs it with `GIT_SEQUENCE_EDITOR=cp '<todo>'`, shell-quoted. A reword becomes `pick` followed by `exec git commit --amend --only --allow-empty --cleanup=whitespace -F '<message file>'`, so no interactive editor runs and commit hooks apply as they do for Git's own reword; a failing hook stops the rewrite and the receipt carries Git's output as a warning. The plan directory is replaced on every rewrite. `GIT_EDITOR=true` accepts the combined squash message, and `--no-autosquash` and `--no-rebase-merges` keep repository configuration from changing the plan. A root range uses `--root`; a shallow boundary is rejected rather than rewritten as a root. A tracked working tree must be clean unless `--autostash` is explicit, and `--autostash` or `--no-autostash` is always passed. Before Git runs, create `refs/gg/backup/rewrite/<unix-nanos>` pointing at HEAD; a backup failure aborts the rewrite.

`gg_git::mutation::rebase_progress` reads an interactive rebase in progress from `rebase-merge`: the done and remaining commit-bearing todo lines with full IDs and subjects, the branch from `head-name`, the count of changed tracked files, and the stop: **Conflict** (unmerged paths), **Reopened** (gg's reopen script was the last line run; carries the base, the original commit and message, and the commits made since the stop), or **Other**. The frame's background summary reads it on load, focus, Local Changes refresh, after a commit, and after each operation.

While a rebase is stopped, the operation area's first line names the stop and step (`Rebase stopped · step <n> of <total> · reopened <id>`, `Conflict · step <n> of <total> · applying <id> <subject>`, or `Rebase stopped · step <n> of <total> · after <id>`, with 8-character IDs), and holds **Resolve conflicts…** when needed, **Continue** (`Ctrl/Cmd+Enter` when no text field has focus), **Skip commit**, and **Abort and restore**. Continue stays disabled, with the reason shown beside it, until conflicts are staged and, at a reopened commit, until no tracked changes remain; it is highlighted once the reopened commit has been committed again. The second line explains what to do; the third shows step chips, each the step's 8-character ID and action as in the mockup (`✓ 0f99a42b pick`; done with a check, the current step highlighted, the next steps; the subject on hover), collapsing far steps into counts. A reopened commit also lists **Commits made at this stop**. Local Changes lists them too, as in the stop mockup: under the STAGED list (wide layout), a `COMMITS MADE AT THIS STOP` section shows each commit's 8-character ID and subject. The menu-bar identity reads `<branch> · rebase <n>/<total>`; the branch button keeps the branch's name, as in the mockup. A newly reopened commit opens Local Changes once with its original message in an empty commit box; a root commit opens in amend mode.

Interactive rebase uses the same Git rebase state and operation area as rebase. Conflicts are read from the worktree and `REBASE_HEAD`, with **Continue**, **Skip**, and **Abort** backed by `git rebase --continue|--skip|--abort`. `git good rewrite --continue|--skip|--abort` exposes the same actions. Completion, skip, and abort refresh history, refs, status, an open reflog, and open backups, and restore the pre-rewrite history row.

**Commit › Interactive rebase from here…** (`R` in History, and the commit-row context menu) starts at the selected commit; the toolbar's **Interactive rebase of this branch** starts at the branch's first own commit. Both open one large modal (`rebase_dialog`) over the current view; the plan rules live in `rebase_plan` and are tested without a window.

- **Header:** **Interactive rebase**, the branch, the result count (`6 commits → 4 · 1 dropped · 1 stop`), the range (`<from>…HEAD onto <base>`, or *the root*), **Cancel** (`Esc`), and **Start rebase** (`Ctrl/Cmd+Enter`). Start is disabled with the first reason the plan cannot run: unchanged plan, a squash or fixup with nothing to combine into, an empty reword message, every commit dropped, or a rewrite already running.
- **Plan (left), newest first like History:** the header reads `PLAN · NEWEST FIRST, LIKE HISTORY` with the key hint `j k select · Alt+↑↓ move · P R E S F D`; squash and fixup rows are indented 12 px under the commit they join; the last row names the commit the plan is replayed onto (`d699f49 base · unchanged`, or *the root*), and a line under the list reads `Keys on the selected row: P pick · R reword · E reopen · S squash · F fixup · D drop`; each row has a drag handle, move up/down buttons (`Alt+Up/Down`), the short ID (hover names the full ID and refs), branch and tag pills when they fit, the subject (struck through when dropped, dimmed when combined), a consequence badge (`↓ squash into <id>`, `↓ fixup into <id>`, `absorbs <ids>`, `⏸ stops here · reopens staged in Changes`, `dropped · recoverable from the backup`), and an action chip. The chip opens a menu of all six actions with a hint and key; unavailable actions stay listed, disabled with the reason. Keys on the selected row: Up/Down or `j/k` select, **P** pick, **R** reword, **E** reopen (`edit`), **S** squash, **F** fixup, **D** drop. Letters wait while the message field has focus. Squash and fixup combine into the nearest kept commit below (older); the oldest kept commit cannot be combined, and the last kept commit cannot be dropped. Badge arrows and the pause mark are Phosphor glyphs.
- **Selected commit (right):** short ID, action, author, and relative date. Reword focuses an editable message seeded with the original, and shows the original subject below it; other actions show the full message. The commit's files and diff appear in an embedded Review (files above the shared reader, no Back button, identity, or status line). Drop dims the reader and says the changes leave the branch. **Open in Review** (`Enter`) holds the dialog and opens the ordinary Review with **‹ Rebase**; leaving Review by any route returns to the same plan.
- **Footer:** **Stash working changes first** (autostash), the other branches and tags that stay on the original commits, and the private-backup notice. Merge commits are rejected with the reason.

The range listing carries each commit's author, relative date, and full message (`gg_git::rewrite::plan_range`, which also returns the replay base). Debug builds open the dialog with `GG_REBASE=<commit>`.

The native rewrite runs on a background worker. Accepted submission closes the configuration immediately; the operation area reports **Rewriting commits…**, then **Refreshing history…** until the replacement history update for the refresh generation is accepted. Browsing stays available, incompatible mutations remain disabled, and the retained pre-rewrite rows are labeled while refreshing. The replacement is adopted only at the existing hover/scroll-safe boundary, so the viewport does not jump under the pointer.

### Backups and recovery

The refs snapshot still excludes `refs/gg/`, so backups never appear as graph labels or ordinary ref rows. **Repository → Recovery…** (Backups source) and the outcome recovery action after a rewrite open the same Recovery window, listing the label, short commit, subject, full private ref, and commit time. ## File reading and history · M7

### Reading surface

The selected-file view has one file identity and three navigation axes: change, file, and commit. **Diff** and **Full file** are two presentations of the same selected file, not separate viewers. Switching presentation keeps the exact path bytes, the Before/After side, and the reading position. The Before/After side applies to full-file reading; the unified diff always shows both sides.

Read one full-file side on the same selected-file worker as the diff, keyed by generation and side. Reuse the diff document for changed-line markers so a mode or side change never recomputes the comparison. Check the blob header before allocating, refuse sides above 2 MiB, and split at most 100,000 source lines. Missing sides, binary content, gitlinks, symlinks, and budget limits return explicit summaries instead of empty text. Cancel before object reads and between projection steps; a superseded generation or side is never published.

Full-file rows are fixed-height and virtualized with exact one-based line numbers. Added lines on the After side and deleted lines on the Before side carry a marker and the same semantic colors as the diff. Clicking a row sets the cursor; Shift-click extends the range. `Up`/`Down` and `j/k` move the cursor, `Shift+Up/Down` extends the range, `PgUp/PgDn` moves by a page, and every movement keeps the cursor visible. The cursor and range are the place used by history.

`[` and `]` move to the previous or next change. In full-file mode a change is a contiguous run of marked lines; in diff mode it is a hunk. Visible **Prev change**/**Next change** buttons perform the same actions, name the current change and total, and stay disabled when the file has no changes. Jumping to a hunk requests the page that contains it from the retained diff document rather than scanning loaded rows.

The back pill reads `‹ History` (or `‹ Files`, `‹ Recovery`, `‹ Rebase`) with a dimmed `Esc`. The Review header names the commit as in the Review mockup: the subject (13.5 px, truncated first), the 8-character ID in a pill, and `author · YYYY-MM-DD` from the comparison. At the right, **Compare with** lists the commit's parent(s) (`parent 7c26d684`, or `parent 2 …` for merges) and **HEAD**; choosing one reloads the comparison in place, and the parents stay listed while comparing with HEAD. Debug builds open a commit in Review with `GG_REVIEW=<commit>`.

`Alt+Up` and `Alt+Down` change the selected file while staying in the reading view. The review header exposes **Prev file**/**Next file** for the same action. The selected file, presentation, and side survive the move; the line position is restored when the new file has that line and clamped otherwise. `Esc` still returns to the file list, and `Enter` opens the selected file.

The place is `{ path bytes, revision, start_line, end_line }`, with one-based inclusive lines and exact path bytes. Engine `Place` stores that identity so path, blame, and line history all use one anchor. A deleted range keeps the before side explicit; history must not silently discard it.

### Shared reader

One reader owns the displayed comparison identity, exact path, both endpoint labels, presentation, inspection side, cursor, anchor, and pixel offset across commit review, staging, and file history. The concrete renderer is the existing `DiffView`; `reader::ReaderContext` is the value consumers exchange. Endpoint labels name the resolved sides (`main (a1b2c3d)`, the parent commit, `Empty tree`, or an older content version) and are shown in the reader header together with the exact modes and blob IDs.

Requested and displayed identities stay separate. A new path, side, mode, or source request increments the generation and cancels superseded work; metadata and rows are adopted together only for the matching identity, and endpoint labels appear only when the displayed content matches that identity. `reader::Capabilities` reports what the current comparison actually supports for Diff, full-side selection, and export, so a label never grants an action. Presentation and side controls never change the comparison; changing the comparison never silently changes the file.

`DiffView::save_context` captures the requested identity, endpoint labels, and place, and `open_context` restores them without creating a second viewer. A restored place survives the asynchronous adoption of the matching content, including an identity change. Commit review saves the context when file history changes the comparison source and restores it exactly once when history closes. The same value is the integration point for staging and later history migration; line/range history mapping remains a separate extension point.

### File and line history

History is a cursor over **content versions**, not over commits. A version is one content state of the followed path; commits that carry an unchanged state are skipped, so the timeline never shows a row that changed nothing. The newest version is the content state the selected revision carries, which may have been introduced by an older commit than the one the review opened. **Full file** shows the current version alone; **Diff** shows the edge `previous → current`. The Before/After inspection sides remain a separate reader control and never navigate versions.

History is a comparison-source mode inside the existing Review reader, not a second content view. Opening it from the reader keeps the file list and review state in place and places a compact version strip directly above the same reader in both the wide side panel and the narrow full-width reading layout. `H` and the visible **History** button open it for the selected path and place. The strip carries **Older version** and **Newer version**, the version counter, and the version's kind, commit, subject, author, date, and old path.

Opening history captures the entry comparison, exact path, revision, presentation, inspection side, cursor/range, and pixel place. Closing history with its button or `Back`/`Escape` restores that context exactly once. Version steps never add navigation or Back history: they change the reader source only. Selecting another file while history is active keeps history open but resets the version cursor to that file's newest content version; the original entry file, comparison, place, and revision stay saved for Close history. Closing returns to that saved entry context and selected file. The previous path's version cursor is never reused. Switching parents leaves history because the comparison revision changed.

Both version directions never wrap: at a boundary the button disables and names the reason — `Oldest version`, `Newest version`, `Only version`, `Loading earlier versions…`, a history limit, or a pending predecessor choice. Loading is a distinct reason from absent: a temporary wait must not read as the end of history. `Alt+Left` and `Alt+Right` perform the same moves.

Predecessor resolution follows carriers of the current content state backwards through parents. If exactly one parent carries the state, the edge is unique and history follows it silently. If several parents carry it and none is a same-state carrier of another, the predecessors are genuinely ambiguous: history stops and shows a chooser in the same version strip with each candidate's kind, commit, subject, author, date, and old path. It never silently takes the first parent. The choice is file-level and becomes the version's edge; choosing a place or hunk inside that edge is a separate question. An edge whose earlier side is not resolved renders the current Full file only, with Diff disabled rather than comparing a file with itself.

A rename is a path-changing edge: the newer version names the new path and the edge names the old path. An absent version is explicit — deletion is a version with no content, not an empty file, and re-adding starts a new added edge. Type changes, additions, deletions, renames, and content changes keep distinct labels. When the trace hits its commit budget, the boundary reports the limit instead of pretending the path starts there.

History preloads a bounded number of versions and pages older ones on demand. The timeline and every version's blob read run on workers keyed by generation; opening another file, backing out, or a newer request cancels the previous work, and a superseded result is never published. A failed page keeps the loaded versions and the pending boundary so a retry resumes rather than restarting. History and blame never move `HEAD`, write refs, or change the index or working files.

`Esc`/`Back` dismisses the active chooser or history source first, then the reading view, then the file list and review, while editor and menu keys retain ownership. `H` while history is open does not stack another history source. Line and range history reuse the same timeline anchored to `Place`. A single line maps through blame first; range boundaries map through diff hunks. When a range spans hunks that diverge into different predecessors, the range asks which predecessor to follow instead of inventing one boundary. A deleted range keeps the before side explicit, and absent versions are identified rather than replaced with empty content. `B` opens blame.

The reader's mode row follows the mockup, in one row: Diff · Full file · Inline · Side by side · **Blame** · **History** · ‹ › · ⋯. **Blame** (`B`) toggles attribution in Full file and, from Diff, opens Full file with blame on; **History** (`H`) follows the file's history (Review shows it on this row; only the narrow file list, which has no reader, keeps History in the Review header); change navigation uses ‹ › (`[` and `]`); the ⋯ menu ends the row; the ⋯ menu also offers **Open in editor**, which opens the file's working copy with the editor from Preferences (or the system's default app) and reports a missing file on the status line.

A segmented **Inline | Side by side** control follows **Diff | Full file** and chooses the Diff layout; **View → Inline diff** and **Side-by-side diff** set the same value, checked for the current layout. The layout belongs to the window (every reader follows it, seeded from the `diff_layout` preference) and is remembered. In Full file the control keeps its slot, disabled with *Full file shows one side; choose Diff to compare*. Side by side shows Before on the left and After on the right, each with its own line number and sign columns; removed lines are tinted red on the left and added lines green on the right. Within a contiguous change, the k-th removed line sits beside the k-th added line and the shorter side is padded with empty cells; context lines appear in both columns, and hunk headers and no-newline notes span both. The diff worker derives the pairing (`split_rows::Layout`) once per document as a list of change runs, so display rows map to unified rows by binary search and rows stay virtualized and paged exactly as inline. Switching layouts keeps the top row in view. Change navigation, keyboard scrolling, the cursor, hunk **Stage/Unstage/Discard hunk** buttons, and changed-line selection for partial staging (click the removed or added cell) work in both layouts. Both columns share one horizontal text offset driven by sideways scrolling (Shift+wheel or a trackpad swipe) instead of a horizontal scroll bar.

Attribution reads one committed path and revision through `git blame --line-porcelain`, with an optional one-based inclusive line range. It is bounded to 2 MiB and 100,000 source lines, refuses binary content, gitlinks, and symlinks rather than pretending to attribute them, and runs on a cancellable generation-keyed worker. It never reads working-tree content; Local Changes disables attribution with that reason. In Full file on either side, **Show attribution** adds an author/short-commit column and `B` toggles it; the After side uses the selected commit and the Before side uses the parent or against revision. Selecting a line names the full author, email, relative time, short commit, and subject. **Open commit** hands that commit to the ordinary review while preserving the caller return location, and **Line history** opens the existing version timeline anchored to the selected line or range. `git good blame PATH [--revision REF] [--lines START,END] [--repo PATH]` prints the same bounded result as JSON.

Line history maps the selected range through each content edge on a cancellable worker. Context lines map to the adjacent version; a line or range introduced by the newer version stops with **Line introduced in this version**; a line or range deleted in the newer version stops with **Line absent in this version**. A range that contains either is reported whole rather than silently shrunk. Opening from the Before side starts the cursor at that older content version, so a deleted line keeps its Before anchor and its Newer edge reports the deletion. An ambiguous file edge uses the existing predecessor chooser before any range mapping; a range is never split across candidates or given an invented common boundary.

### Worktrees

`git worktree list --porcelain -z` is the read-only inventory. Each row names the exact path bytes, short branch or detached/bare state, HEAD, current/main flags, lock and prunable reasons, and dirty status from a bounded `status --porcelain` read in that worktree. The **Repository → Worktrees…** window lists this inventory with **Open**, **Create worktree…**, and a separate **Remove…** confirmation. Missing, locked, dirty, main, and current worktrees keep an explicit reason instead of offering a force or delete-files route; pruning a missing registration is not offered here.

Create chooses an exact destination and either an existing local branch or a new branch with a start revision. The destination must be absent or empty, and a branch checked out elsewhere is named with its path instead of being forced. Add runs on a worker, keeps the dialog on failure, and lists the worktree only after Git succeeds. Open saves the current worktree's commit/file selection, filter, reading place, and Local Changes draft before loading the target; each worktree restores its own saved selection and draft, and a new worktree starts empty. Remove re-lists, rechecks dirty/lock/current/main state, confirms the exact path and branch, and runs `git worktree remove` without force. CLI `git good worktree list|add|remove` returns the same inventory and receipts as JSON.

### Submodules

A gitlink's **Submodule details…** action is available from the shared reader's File actions menu. It names the exact path, Before/After recorded commits, parent index commit, nested HEAD, initialization and dirty state, `.gitmodules` URL and branch, configured URL differences, recorded-object availability, and any missing `.gitmodules` or status detail. Historical review keeps Before and After recorded IDs separate from the nested checkout; browsing never initializes, checks out, stages, or fetches a submodule.

Update targets the parent index gitlink and is blocked when the selected recorded commit differs from the index, when the nested tree is dirty, or when the recorded object is missing locally. The confirmation names the path, target commit, and URL, states that Git may fetch, and states that the parent index is not staged. Update runs on a worker, initializes with `git submodule update --init -- <path>`, and rescans the nested and parent status. **Open nested repository** switches to the initialized nested repository as its own context; the parent selection and draft remain in the per-worktree state map. CLI `git good submodule status|update PATH [--repo PATH]` returns the same details and receipt. Network use is explicit in the confirmation; no automatic recursive update, force, or parent staging is added.

### Git LFS

LFS-managed content stays a pointer until an explicit fetch. Pointer detection parses only the canonical v1 header, `oid sha256:` (64 hexadecimal digits), and `size` line, with bounded input and explicit malformed states. **File actions → LFS details…** names the exact path, Before/After pointer OID and declared size, whether each object exists under the repository's LFS object store, whether `git-lfs` is available, and the selected remote. A non-pointer file reports that explicitly; pointer text is never presented as the fetched content.

Local Changes uses the same details window with sides taken from the selected area: Staged compares the HEAD entry with the index entry, Unstaged compares the index entry with the bounded working file, and Untracked compares an absent Before with the working file. An unmerged path reports that the conflict must be resolved instead of presenting an index stage as content. Working-file pointer reads stop at 4 KiB and never smudge or materialize content.

When the selected object is present locally, the details window loads a bounded content preview on the worker: objects up to 2 MiB are decoded as PNG/JPEG when possible and otherwise shown as the existing bounded hexadecimal preview. Missing, over-budget, unreadable, and non-image content stay explicit; export continues to use the complete original bytes. Previewing never writes a working file, stages, or imports external content.

**Fetch object…** is enabled only when a target object is missing and `git-lfs` is available. The confirmation names the OID, size, and remote and states that fetching may download data and does not change or smudge working files. Fetch runs on a worker with `git lfs fetch [REMOTE] --include=<path>`, then rescans object availability; no automatic network, smudge, materialization, staging, or working-tree write is added. CLI `git good lfs status|fetch PATH [--area staged|unstaged|untracked|conflict] [--revision REF] [--before REF] [--repo PATH]` returns the same details and receipt for review-time or Local Changes pointers. Smudging/materializing fetched content into working files remains planned and must stay an explicit action.

### Signing

**Verification.** Commit details exposes **Signature details…**, and a tag's ref menu exposes the same action. The window and CLI resolve the object type and run `git verify-commit --raw` or `git verify-tag --raw` through the repository's configured signing tool. Git's raw status is parsed into separate fields: unsigned, good, bad, unknown key, verification unavailable, or error; signer identity, key fingerprint/ID, trust label, declared format, and the underlying detail. An unsigned object is not an empty success, an unknown public key is not a bad signature, and a valid signature is reported separately from its trust. Verification is read-only: it never imports keys, changes trust stores, or writes repository signing configuration. `git good signature config|verify [REF] [--repo PATH]` returns the same configuration and verification as JSON.

**Configuration.** The signer reads `gpg.format` (default `openpgp`), `user.signingkey`, `gpg.program`, `commit.gpgsign`, `tag.gpgsign`, and `gpg.ssh.allowedSignersFile` through normal Git configuration inheritance, and reports whether the configured signing tool is available. The application never writes these keys. Configuration, validity, and trust remain three independent facts in the window.

**Signed commits.** Local Changes shows a **Sign** choice next to Amend, initialized from `commit.gpgsign`; it is enabled only when a signing key is configured and the tool is available. The choice is captured with the draft, so view and repository switches do not silently change it. When signing is requested, the commit worker runs the normal pre-commit/prepare-commit-msg/commit-msg hooks, then asks `git commit-tree -S` to sign the observed tree, parents, message, and pinned author/committer identities. Only after signing succeeds does the app update `HEAD` under the reference lock and run post-commit/post-rewrite. A missing key, unavailable tool, or agent failure aborts before any reference update and keeps the message, index, and working tree; there is no unsigned fallback. The status line names a signed commit, and CLI `git good commit --sign` follows the same contract. Without an explicit flag, the CLI follows `commit.gpgsign`; `--no-sign` is an explicit opt-out.

**Signed tags.** **Branch → New tag…** is available from the Branch menu and the toolbar at every width. The dialog requires a name, explicit target (the selected commit or `HEAD`), and annotated message. **Sign tag** is initialized from `tag.gpgsign` and disabled with a reason when the key or tool is unavailable. Creation runs `git tag -s` (or `git tag -a` when unsigned) on a worker; failure leaves no tag and keeps the dialog fields, while success refreshes refs. CLI `git good tag --create TAG --at REF -m MESSAGE [--sign|--no-sign] [--repo PATH]` returns a receipt with the tag, target, object ID, and signed state; tag signature verification uses the same Signature details or `git good signature verify`.

### Deferred large-repository features

Materializing or smudging fetched Git LFS objects into working-tree files and image blend modes beyond normal-alpha onion skin (such as difference heatmaps) remain planned follow-ups. Neither is represented by a placeholder control.

# Architecture

Purpose: define system boundaries and behavior contracts.

## Layers

| Crate | Responsibility |
| --- | --- |
| `gg-engine` | Typed commands, incremental readers, filtering |
| `gg-git` | Repository discovery and object access through gitoxide |
| `git-good` | CLI, egui/eframe on wgpu, view state, workers |

Dependencies flow from shell to adapter to engine. Keep the engine independent of Git libraries, UI, and platform services. CLI and UI share commands. Add abstractions for concrete responsibilities.

## Runtime

Use safe Rust and propagate errors with operation, path, and retry. Preserve objects, refs, index, and working files while browsing. Keep native paths in APIs and exact object identities; use Unicode for editable paths and replacement characters for display text.

Run Git reads/indexing on workers, publish immutable batches, and repaint for visible changes. Retain displayed results through loading and errors, labeled with their repository identity. Track requested and displayed repositories separately.

### Git processes

Every Git process starts at one chokepoint, `gg_git::process::git()`, which returns a `GitCommand`: a builder over `std::process::Command` with the same `arg`, `env`, `current_dir`, `stdin`/`stdout`/`stderr`, `output`, `status` and `spawn`. Each caller keeps its own arguments and environment (`env_remove("GIT_DIR")`, `--literal-pathspecs`, `--no-optional-locks`, null stdin…). A test, `git_processes_start_at_the_chokepoint` (crates/git/tests/chokepoint.rs), fails on any `Command::new("git")` in production code of `gg-git`, `gg-engine` or `git-good`; test helpers and `build.rs` are exempt. The chokepoint points `GIT_TEXTDOMAINDIR` at a folder that cannot exist (inside Git Good's own executable file), so Git finds no translations and writes its messages in English whatever the user's locale: Git Good tells some failures apart by Git's message (a rejected push, nothing to stash). The locale is not touched, so what Git starts (hooks, credential helpers, editors) keeps the user's language; only Git commands a hook runs speak English. Where the executable's path cannot be read, it sets `LC_MESSAGES=C` and drops `LANGUAGE` instead (a set `LC_ALL` moves to `LC_CTYPE`).

Spawning checks one relaxed atomic; only while a test holds a `process::Recording` does it take a lock and note the command line. A recording keeps the spawns that name its roots (in an argument or the working directory), with each root replaced by a placeholder such as `<repo>`, and whether the spawn ran on the recording's own thread (the UI thread in GUI tests), so tests running in parallel never see each other's processes. The RULE-16 parity tests (XCT-30) use it to compare the GUI's command lines with the CLI's, and to assert that no GUI mutation starts Git on the UI thread.

The UI thread never waits for Git. Every mutation runs on a worker that publishes its receipt when it reports back: switch and branch creation with a switch on the branch worker, fetch and push on the network worker, commit on the Local Changes commit worker, tag creation on the New tag worker, and everything else (stash push, apply, pop and drop; branch create, rename and delete; tag delete; reset; cherry-pick and revert; merge, rebase and their recovery; conflict staging) on the one operation worker described under [Merge, cherry-pick, revert, and recovery](#merge-cherry-pick-revert-and-recovery). The signing configuration (`gg_git::signature::config`: six `git config --get` reads and a probe of the signing tool) is read by `signing_cache.rs` in the background when Local Changes or New tag opens, when the window regains focus while either shows it, and when the watcher reports a change to the repository's `config`; each view shows the last configuration read until the new one lands. The commit worker waits for a read in flight or reads it itself before committing, and the tag worker waits for New tag's read, as `git good --cli commit` and `git good --cli tag` read it to choose signing; either refuses to sign with a setup that cannot. `gui_mutations_cost_what_the_cli_costs` (`parity_tests/timing.rs`, run nightly by `.github/workflows/timing.yml`) times each mutation from the call its control makes to the receipt applied, against its CLI handler.

## Launch

Resolve the repository from cwd, including nested directories, or an explicit path. Interactive launch loads history immediately; the toolbar supports repository changes. Launched outside a repository, Git Good shows the welcome view (see Presentation) with the launch folder's amber line; a launch path inside a repository opens that repository. CLI history streams JSON; failures use stderr and nonzero status. Represent bare repositories, worktrees, unborn branches, detached HEAD, and shallow boundaries explicitly.

**Diagnostics** (`diagnostics.rs`). Opening a window starts a log, `gg/logs/gg.log` under the configuration folder; the previous run's is kept as `gg.previous.log`, and a run stops writing at 16 MiB with one line saying so. Entries are `<UTC time> <kind> <text>`: the launch (version, commit, build date, target, OS, then Git's version read off the main thread), error outcomes with their details, panics with thread, place and backtrace (a hook in front of Rust's own report), a failed launch, and slow frames. A frame is timed in stages (`frame_stages.rs`: polling, toolbar, refs sidebar, dialogs, views); one that takes 50 ms or longer logs `slow-frame <total> (<slowest stages>); command <command>`, naming its three slowest stages and the toolbar or menu command it ran, at most once per 2 s, the slow frames in between counted on the next line. Passwords in `scheme://user:password@host` URLs are written as `***`. A launch that fails prints the error and, when stderr is no terminal (a desktop launch), shows a native error dialog naming the log. CLI commands and tests log nothing. The window's wgpu setup drops the OpenGL backend on Windows and wgpu's indirect-call validation everywhere, two known driver crashes; `WGPU_BACKEND` and `WGPU_VALIDATION_INDIRECT_CALL` still override them.

## History sessions

Pin each session to repository identity and resolved HEAD. Carry generations through requests/results; apply current results. Refresh creates a replacement session, adopted when ready and interaction permits. Repository switches clear the old filter/selection; refresh preserves matching selection by ID, otherwise the first visible result.

Traverse the deduplicated union of commits reachable from HEAD and every local branch, remote branch, and tag. A single tip uses the incremental frontier: emit the newest committer timestamp, break ties by descending object ID, then enqueue parents. Divergent non-shallow tips use topological order so parents follow all children. Repositories with more than 512 divergent tips delegate that topological ordering to `git rev-list --topo-order --stdin` and read metadata through gitoxide; smaller graphs keep the in-process topo builder. The refs snapshot is reused so a large multi-ref repository is not scanned twice. Assign stable ordinals and retain continuation state; shallow traversal stops at recorded boundaries. Every reachable commit remains accessible.

Prioritize visible rows, overscan, then indexing/counting. Publish summaries, selected details, progress, completion, and errors. Summaries carry ID, subject, author, and date; selected details include full message and parents.

### Storage and budgets

| Resource | Contract |
| --- | --- |
| Traversal slice | At most 32 commits or 4 ms; foreground work between slices |
| Requests/responses | One coalesced slot each |
| Response page | Up to 256 summaries; cache the current worker page |
| UI cache | At most 768 rows and one selected full message |
| Session files | Commit records, fixed-size ordinal offsets, separate filter offsets; close with session |
| Graph state | Frontier/visited IDs scale with graph size; release visited IDs on completion |

Reuse records across viewport and filter requests. Retain rows and mark counts incomplete after storage/traversal errors.

### Count and interaction

Publish discovered count, optional approximate estimate, and completion. Use valid count information as a hint; otherwise show the growing discovered extent. Counting shares the ordered history index and ends with an exact total.

Anchor by commit ID and pixel offset. Preserve that anchor as the range grows. Freeze scrollbar geometry only while the thumb is dragged, and preserve the thumb's grab offset; otherwise the extent follows the count as it grows. Deep jumps show fixed-height loading slots and traversal progress.

**Targets never swap under a click** (`target_guard.rs`, shared by History, Local Changes, Review and the reader). New content shows as soon as it arrives: history pages, counts, filter results, watcher refreshes, status lists, comparisons and diff pages. What holds still is what the user aims at. The scroll position is anchored by identity (commit ID or path, plus pixel offset), so rows added above the view never push it; selection and focus follow identity; the scrollbar keeps its extent and grab offset while dragged; unfilled slots keep their fixed height and fill in place. When the row under a pointer that stayed put changes identity, that row fades its new content in over 0.25 s and refuses clicks for 0.3 s, just above reaction time, so a click already on its way is dropped instead of acting on the new row; a press and its release act only on the row that was pressed. The user's own motion (moving the pointer, scrolling, dragging) never starts that grace, and an animation the user starts, such as a folder opening, may move rows slowly enough to see. History holds HEAD and every ref, so a switch from one branch to another existing branch changes no row and does not read the history again: HEAD moves (current-branch marker, branch button, window title) and the new tip is selected in the list already shown, the moment Git's switch returns; the watcher does not re-read for that HEAD change. Creating a branch on switch, or leaving a detached HEAD, reads the history again, and that read replaces the list on its first page, at the new tip.

### Filtering

Each edit increments a revision, including repeated text. Preserve edits during opening/refresh and apply matching revisions. Search full messages progressively in traversal order; distinguish partial, complete, and empty results.

Preserve matching selection; otherwise select the first published match. Clear selection/details at zero matches. Apply result and selection changes together as they arrive. External changes produce a refresh indication; explicit refresh adopts them. Implementation gaps: [regression inventory](regression.md#remaining-coverage).

| First / last row | Home/End, also with Ctrl (Command on macOS), in History, the Local Changes lists, the Review file list, the reader, Recovery, Submodules and Worktrees; End before counting finishes goes to the last row found so far |
| Open selected commit/file / return | Enter or Right / Escape, Left, or Back |

| Next / previous region | F6 / Shift+F6: the toolbar's search field, the docked refs sidebar's filter, the content (the list, whose keys work while no field has focus), wrapping; a region not shown is skipped (`a11y.rs`) |

AccessKit is on (eframe's `accesskit` feature): screen readers see egui's widget tree, with the names and disabled reasons the widgets give; egui builds it only while an assistive technology asks. Only F10 alone puts the keyboard on the menu bar; Shift+F10 is the context menu key.

**Keys of the window commands** (`keymap.rs`) come from one table: Open (`Ctrl+O`), Quit (`Ctrl+Q`), Fetch, Pull and Push (`Ctrl+Shift+F/L/P`), New branch (`Ctrl+B`), Switch to (`Ctrl+Shift+B`), Rename (`F2`), Delete (`Del`), Reword (`Ctrl+R`), Stage all and Unstage all (`Ctrl+Shift+S/U`), Stash changes (`Ctrl+Shift+Z`), Back and Forward (`Ctrl+[`/`Ctrl+]`) and Keyboard shortcuts (`?`). The menus label them from it, the macOS menu bar's key equivalents follow those labels, dispatch reads it, and Help lists the menus. A press runs the command whose chord has exactly its modifiers (Ctrl+F never runs a Ctrl+Shift+F command; `?` matches with or without Shift); keys without Ctrl or Alt act only while no field is typed in. Preferences › Keyboard lists them under **Commands**: clicking a key waits for the next press (Esc cancels) and takes it unless the window keeps it (`Ctrl+1`, `Ctrl+2`, `Ctrl+K`, `Ctrl+F`, `Ctrl+\`, `Ctrl+,`, the text-editing chords, `Ctrl+Enter`, `Ctrl+S`, `Alt+A`, `F6`, `F10`, `Shift+F10`), another command has it, or it is a letter or other list key on its own; the refusal names the reason. **Reset** puts one back, **Reset all keys** all of them. Changed keys are saved as `keys` (command id → chord) in the settings file; an entry that does not read or clashes keeps the default. The other keys are listed under **Fixed keys**.

The in-window menu bar works from the keyboard (`menu_keys.rs`, adapted from photocraft): a tap on Alt — Alt pressed and released with no key, wheel, click or window switch in between — or F10 puts the keyboard on the bar with the first title lit, and the History and list shortcuts wait while it is there; a command shortcut (Ctrl/Cmd with a key, or a function key other than F10) leaves the bar and runs in the same press. Alt+letter opens the menu with that mnemonic from anywhere, and in an open menu a letter runs the row with that mnemonic or opens its submenu. Mnemonics are assigned per menu level from the labels as shown, unique within the level: the top menus take **R B C N I H** (`Git Good` **G** on macOS), and no top menu takes **A** or **V** because Alt+A opens the commit actions and Alt+V pages up; rows take the first unused letter, word starts first. They are underlined while Alt is held, the bar has the keyboard, or the menu was opened from the keyboard; a menu opened with the mouse shows none until Alt is pressed. While the bar or a menu has the keyboard, a focused text field below types none of its letters. Open menus behave like native ones (`menu_nav.rs`, adapted from photocraft): Up/Down move one highlight shared with the pointer and drawn like a hovered row, skipping disabled rows, wrapping, and kept in view; Right opens the lit submenu (first row lit) or the next menu, Left closes the submenu or opens the previous one, Enter/Space run the lit row, Esc closes. egui's own arrow-key focus is suppressed in these menus so only one row is ever lit; the commit actions popup, context menus and choice lists keep egui's Up/Down/Enter/Esc focus navigation. A menu or submenu taller than the window stays below the menu bar and inside the window and scrolls: by the wheel, by the keyboard, and with ▲/▼ strips at its ends that scroll at 600 pt/s while the pointer rests on them. An open submenu stays open, its row lit, while the pointer heads for it inside the triangle from where it left the row to the submenu's near edge (24 pt slack above and below), on a diagonal or curved path or with a pause shorter than 0.3 s; resting longer on another row, leaving that triangle, a click or a key lets the row under the pointer take over. While one menu is open, moving the pointer onto another title opens that menu; a pointer resting on a title does not undo Left/Right. On macOS, when the native menu bar replaces the in-window one, none of this runs.

Emacs bindings use physical Control. Ctrl+V retains native paste. Escape leaves filter focus. Text editors and open menus retain editing/navigation shortcuts; focused buttons allow list navigation. Reading views use Up/Down, j/k, Ctrl+P/N, and page keys to scroll their content. Enter opens a full-width diff from either file-list layout. History bindings apply while history is visible and editors are unfocused. Empty results keep selection empty. The status hint keeps the core bindings readable at narrow widths instead of clipping; the Help window lists the full set.

The **Actions** menu in the commit inspector, the commit-row context menu, and the Alt+A route draw the **Commit** menu's own entries from the one command table (same labels, shortcuts, and disabled reasons) as 24 px rows with the empty check column and shortcuts at the right, without group headings or hashes in the labels: Review changes, Compare with HEAD, Copy ID with **Copy subject** and **Signature details…** under it; Cherry-pick onto HEAD, Revert; Interactive rebase from here…, Reword…, Reopen for editing…, Fixup into…, Drop… (red; these four open the rebase plan with the commit preset); then **Reset current branch to here ▸** (red) with **Soft · keep index and files**, **Mixed · keep files** (checked, `default`), and **Hard · discard changes…** (red). Recovery… lives in the Repository menu. When the mutations share one disabled reason, they keep their rows, greyed and without per-row tooltips, under one amber band above them that gives the reason (`Rebase in progress. Continue or abort it to change commits.`). Right-clicking a row selects it first, because the Commit menu acts on the selected commit. **Several commits** are picked as in Local Changes: Ctrl/Cmd-click adds or removes a row (the first one keeps the selected commit), and Shift-click or `Shift+Up/Down` picks the rows from the anchor (the last row clicked without Shift) to the clicked one; a range reaching rows not loaded picks nothing and the footer says *Pick a shorter range: N of its commits are not loaded.* Picked rows share the selection fill and the footer starts with `N commits selected`; new rows (a reload or a filter) end the picks. With two picked, **Compare with HEAD** reads **Compare these two** and opens Review on the newer commit against the older; with two or more, **Copy ID** reads **Copy N commits** and copies one `id subject author date` line each, newest first (also `Ctrl/Cmd+C`), and **Cherry-pick onto HEAD** reads **Cherry-pick N commits onto HEAD** and applies them oldest first with one `git cherry-pick`, as `git good --cli cherry-pick A B …` does; the other commands act on the selected commit. At wide widths the selected commit is shown in a 58 px **commit inspector** under the history list (the History mockup): avatar, subject (13.5 px, full message on hover), the 8-character ID in a pill (click copies the full ID), **Review** (`Enter`) and **Actions** (`Alt+A`), and a second line with author, date, parent(s), and, once a background count against the first parent finishes, `· 5 files +86 −41` (added lines in the diff's added color, deleted in its deleted color; counting stops after 2,000 files or two seconds and then reads `2000+ files`). The count appears at the end of the line, so nothing moves while it loads. View › **Commit details** (`Space`) shows or hides it; the refs sidebar keeps the full height. Below 1040 px the inspector adds **Details** (`Space`), which replaces the list with the commit details (below); Alt+A opens the details first and then the same popup from their **Actions** button. **Help › Keyboard shortcuts** (`?`, or **Show keyboard shortcuts…** in Preferences › Keyboard) opens a non-modal window (`shortcuts`) with one key | action table generated from the command table: each menu's items that have a key, grouped under the menu's title in menu order, then the list scopes whose single keys act on a focused list (History list, Changes list, Review, Rebase list, Conflicts, Stashes). A filter field matches keys or actions, ignoring case, and groups with no matching row hide. There is no Refresh row (`Ctrl+R` is Reword). `Esc` or × closes it; **Edit keys…** closes it and opens Preferences › Keyboard. **Help › About Git Good** uses the dialog frame (title and × in the first row, the footer below): the logo, version, a label grid with **Commit** (8 characters, from `build.rs`), **Built** (`YYYY-MM-DD · <target triple>`, UTC, honouring `SOURCE_DATE_EPOCH`), author, license, and source, the AI-assistance note, then **Copy version info** (six plain lines: `Git Good <version>`, `commit <id>`, `built <date>`, `target <triple>`, `git <version>`, `os <system> (<release>) <architecture>`) and **Close** (`Esc`). The visible control, the context menu, and the shortcut invoke the same command for the same target, readiness reason, and confirmation.

Truncated fields end in a real "…" button whose accessible name names the field (`Show full commit subject`). It opens a non-modal full-text window titled by the field (**Commit subject**, **Path**, **Parents**, **Commit message**, **Error**, **File details**): the exact text, selectable, in mono for paths and IDs, then `<n> characters · text is selectable`, **Close** (`Esc`), and the primary **Copy** (`Ctrl+C`).

Opening a commit or comparison from History or Details records a return location with the exact selected commit ID, filter query, and pixel offset, plus whether the narrow commit details were the caller. Closing Review restores that location once. Review presentation changes do not add return locations or Back steps. Recovery records its source, the Reflog reference filter when present, and the source-specific selected entry; closing Review returns to that Recovery entry and filter, not to History.

The operation band sits directly beneath the toolbar only while Git holds a merge, rebase, cherry-pick, or revert open, or a rewrite runs; there is no idle band, and the current branch and its tracking appear only on the toolbar's branch button (`operation_band`). It has a fixed two-line height, so a stop's own changes never move the panes below. Line 1 holds the icon, the title (`Merge conflict · merging origin/main 0f51a473 into main`, `Cherry-pick conflict · applying 9a4f9a95 onto main`, `Revert ready · reverting 7151cc83 on main`, with the 8-character ID in monospace), the status right after it at normal size (`2 conflicts left in 2 files`, `All files staged`, or why Continue waits), and the buttons; line 2 holds the explanation (`Ours is main, Theirs is origin/main. Resolve and stage each file, then continue.`) followed by the step chips when the operation has steps. The title truncates first, with the full text on hover; the status keeps its slot. The band is amber (warning glyph) while conflicts remain and purple (pause glyph) once nothing is conflicted. Buttons: **Resolve conflicts** (the filled primary, hidden while the conflict workspace is open), **Continue** with its `Ctrl+Enter` hint (disabled with the reason in the status while files are conflicted, the filled primary once they are not), **Skip commit** (not for a merge), and red **Abort and restore** (`Abort the merge and restore main to its previous tip`). A Continue, Skip, or Abort click keeps the band and its layout: the icon becomes a spinner, the title takes the worker label (`Continuing merge`, `Skipping cherry-pick`, `Aborting revert`), the explanation says what Git is doing (`Writing the merge commit…`), and the buttons disable in place. An operation found on launch shows the same band. The step strip has no scroll area: done steps collapse to `✓ n done`, the current chip always shows, then the next chips that fit, then `+N next`, with the full plan in the tooltip; chips never overlap the explanation or leave the band. While a rewrite runs the band is purple with a spinner, `Rewriting <branch> · step <n> of <m> · picking <id>`, `Browsing stays available; the old history is labelled until the new one is accepted.`, and the step strip from Git's own todo (read beside the rewrite), with no buttons: Git is writing, and the footer names the backup (`Backup: refs/gg/backup/…`) as the way back. Then it reads `Refreshing history…` (spinner, every step ✓) until the replacement generation is accepted. Short jobs (network, branch work, a merge, rebase onto, or pull that never stops) report in the footer instead and never show the band. Duplicate submission is refused and incompatible mutations stay disabled. The band is the only place for its controls; dialogs, the toolbar, and the footer do not repeat them.

Operation outcomes carry a severity, a concise summary, optional full details, and at most one recovery action. The 22 px footer (`footer`) shows one message, by priority: a failure, then something blocked, then a running job, then a receipt, then the key hints. Messages name the job and its target without prefixes such as `History ·` or `Network ·`: network progress reads `Fetching origin · Receiving objects 42% · 812/1930` with a thin progress bar and **Cancel** (`Starting push…` until Git reports; Cancel turns into `Cancelling fetch…`, `waits for Git to stop`), `Pushing <branch> to origin`, `Cloning gg`; branch jobs read `Switching to <branch>…`, `Creating <branch>…`, `Creating <branch> from origin/<branch>…`, or `Stashing 3 files and switching to <branch>…`; Merge into current, Rebase current onto, and Pull start as footer jobs (`Merging origin/main into main…`, `Rebasing main onto origin/main…`) and leave a receipt when they finish cleanly (`Merged origin/main into main · 3 commits`); the band appears only if Git stops. Receipts carry a check and no prefix, with the grey part after the first ` · ` (`Pushed feature/rebase-ui to origin · upstream origin/feature/rebase-ui`, `Rewrote 4 commits · backup refs/gg/backup/…` with **Recovery…** and **Details…**), plural forms throughout, and fade back to the key hints after 8 seconds. **Undo.** The receipt of the last reset, rebase, rewrite (when it needs no push), or branch delete offers **Undo**, and so does the Local Changes status line after a commit or amend, in the slot Retry takes after an error. Undo puts back what the operation changed, from what Git Good already has: a reset, rebase or rewrite restores the branch to the backup it saved, as Recovery's Restore does (refused while the tree has changes; the tip it replaces is saved as a backup first); a commit or amend moves the branch back to the commit's parent or the commit the amend replaced with a soft reset, so the committed changes are staged again and files are untouched; a branch delete creates the branch again at the tip the refs list had. Only the last operation can be undone: starting any other operation, switching repository, or the undo itself (whether it works or is refused) forgets it. It runs on the operation worker like the operation it undoes and reports `Undone: …`. Failures are red on a tinted footer with one recovery action, **Details…** when full text exists, and ×, and stay until dismissed or the next job starts (`Push rejected: … · fetch first` offers **Fetch**; a fetch failure offers **Retry fetch**, which waits until the repository was re-read). Blocked actions are amber in the same slot with one action: `Can’t switch to feature/rebase-ui: 3 changed files would be overwritten` offers **Stash and switch** (or **Retry switch** when stashing is not the fix); × clears the retained intent without executing it. A network error's first line is the summary and Git's remaining output its details. **Details…** opens a non-modal, resizable window titled by the operation (the summary up to its first `: ` or ` · `, then ` · details`, for example `Push rejected · details`; `outcome_details`): the plain-language summary line, then Git's raw output in monospace, selectable and scrolling both ways, and a footer with **Copy details**, **Close** (`Esc`), and the footer's same single recovery action as the filled primary (`Enter`).

Follow [bounded-reveal rules](design.md). Page by the rendered viewport with one row of overlap, clamp at history boundaries, and stream uncached destinations. Show cached selected metadata immediately; reserve the full-message slot while loading. Narrow details preserve hidden history selection and pixel offset.

Rationale: one bounded reveal preserves spatial context; overlapping pages retain reading context; fixed details slots keep loading visually stable.

## Presentation

Apply [design guidelines](design.md). Dialogs that ask for a decision or start a change (create, delete, merge, rebase, track, reset, stash, restore, drop, clone, force push, worktree and submodule changes, LFS fetch, export, base folders) and **Preferences** are modal: they sit above a dimmed backdrop that absorbs clicks and drags, and History, reader, and list navigation keys stay with the dialog until it closes. Tool and information windows (Stashes, Recovery, Worktrees, details, Keyboard shortcuts) stay non-modal so browsing continues beside them. **Automatic refresh.** There is no Refresh command. A file watcher watches the worktree and the Git directories: on Linux, inotify directly, asked only for created, deleted, moved, written-and-closed, and mode-changed entries, and kept out of the Git directory's objects and logs; elsewhere the `notify` crate (FSEvents or ReadDirectoryChanges). notify's inotify backend always asks for open events, and Git opens hundreds of files per command, so with it every command took 2–3 ms longer while a window watched its repository (RULE-16). Changes are sorted into working files, the index, and refs or operation state (HEAD, refs, `packed-refs`, merge, rebase, cherry-pick, and revert state); objects, logs, and lock files are ignored. After 300 ms without events, measured from when the watcher saw the last one, a ref or operation change reloads the history (unless a load already started after the change) and the worktree status; other changes re-read the status and the frame summary. Each event wakes the window; while changes are still settling, the frame that drains them asks for another frame at the moment they settle, so an idle window shows them without input, and with nothing pending it schedules none. When the system cannot watch an open repository (inotify out of instances or watches, a file system without change events), a warning says so once, with the reason in **Details…**, and the window re-reads the history, status, and signing configuration each time it gets focus back; every later load tries the watcher again. Before any menu, toolbar, search, or shortcut command runs, unsettled changes are applied at once and the operation state is re-read. Refreshes keep the previous content in place until the new content arrives. `Ctrl+R` is **Reword…** and `Del` (in History, with no popup open) is **Delete…**.

The OS window title reads `Git Good — ~/path` (the home folder shortened to `~`), followed by ` — rebasing <branch> · step <n> of <total>` or ` — rebase conflict · step <n> of <total>` while a rebase is stopped. Use a menu header, one stable toolbar beneath it, one operation band while Git holds an operation open or a rewrite runs, a history column header, and fixed-height status line. Reserve counts/progress/errors. Show full paths on hover and edit paths explicitly. The 26 px menu bar (an egui menu bar: frameless titles, hovering moves between open menus) holds **Repository**, **Branch**, **Commit**, **Changes**, **View**, and **Help**, no logo (the titles start the bar) and the window identity (the same text as the OS window title, plus `shallow` for a shallow clone); the branch is not repeated there. On Windows and Linux the menu bar is the window's title bar ([final design](final-design.md#window-frame)): `titlebar` draws it, centres the identity in the free gap, owns the caption buttons, the drag gap and the edge resize zones, and ends the press of an OS move or resize whose release the compositor keeps (`raw_input_hook`); the window opens undecorated unless `system_title_bar` is set, read before the window opens. `caption_style` works out the Linux desktop's caption buttons once, off the UI thread (desktop variables, GTK `settings.ini`, `kwinrc`, and GNOME's `button-layout` through the settings portal via `gdbus`, else `gsettings`). ## Commit review · M1 specification

### Comparison

Pin repository, commit, and parent IDs. Resolve revisions once. Default to first parent; roots compare with the empty tree. List merge parents in stored order with one-based numbers, short IDs, and full-ID tooltips. Parent changes reuse the pinned commit ID. Missing parent objects produce an identified incomplete-comparison state; retain metadata during loading/errors.

Keep exact Git path bytes and a one-line display string. Preserve Unicode; escape backslashes, controls, and invalid bytes (`\xNN`) so distinct paths have distinct labels. Copy Unicode paths verbatim; label the fallback **Copy escaped path**. CLI `--file` matches native path bytes. Changes carry old/new object IDs and modes, with added/deleted/modified/type-changed status. CLI and UI share deterministic Git tree traversal order. Represent moves as deletion/addition in M1, retaining both sides for future rename detection.

Parent switches retain the displayed comparison through loading/failure, label its identity, and offer retry. Adopt replacement files and diff together as soon as both arrive. Start the new comparison at its first file; empty comparisons clear selection. Independent worker mailboxes isolate superseded requests.

### Loading

Stream file summaries before blob reads. Virtualize rows using history's paging and interaction rules; counts progress to exact completion. Within a comparison, preserve selection by exact path, otherwise first result; clear it for empty comparisons.

Keep requested and displayed file identities separate. Retain the displayed diff and its scroll offset while a replacement loads; publish its identity, metadata, preview, and rows together as soon as they arrive, even under a resting pointer. Later pages fill their empty slots in place when they arrive. The reader keys the target guard on the document line under the pointer (file, working area, and the row's kind, line numbers, and text, or its unread slot), never on its screen slot: a line that changes under a still pointer fades in and refuses clicks, including its hunk Stage, Unstage, and Discard buttons, for the grace above. Errors retain labeled previous content. Reset the new file to its first row on adoption.

Panes never show loading text ([design rule](design.md)). Finished empty scans explain themselves in the pane, centered, as in the empty-states proposal: with no repository open, a welcome view replaces History: the toolbar holds only search (*Search repositories and actions*, listing recent repositories under Repositories and every menu command under Actions; its icon below 760 px), with no sidebar toggle, Changes/History tabs, Fetch/Pull/Push or branch button, and no refs sidebar, History header or inspector; the menus stay complete, with repository commands disabled as *Open a repository first*. A centered 640 px column 44 px from the top holds the 36 px logo, **Open a repository**, and the weak line `Git Good <version> · Git <version>` (Git's version read once in the background into its reserved slot; logo and line hide below 760 px); three equal cards **Open…** (filled, *A folder on this computer · Ctrl+O*), **Clone…** (*From a URL into <preferred clone folder>*) and **New repository…** (*git init in a folder*), with shorter subtitles when narrow; then RECENT with its count and up to ten 22 px rows: folder name (132 px), the path with `~` (mono, truncating, full path on hover), the checked-out branch (128 px, read from HEAD in the background, blank until read, dropped first when narrow), when it was last opened (76 px: `2 h ago`, `yesterday`, `3 days ago`, `Oct 12`), and × on hover or selection. The first row is selected; ↑ ↓ move, `Enter` opens, `Del` or × removes the entry from the list only. A missing folder stays listed, dimmed, with an amber `missing` chip. Opening a row keeps it selected and the footer reads `Reading <path>`; a row that fails turns into one amber line in its slot: `<path> no longer exists.` with **Remove from recent** and **Locate…** (the picked folder replaces the entry and opens), or `<path> is no longer a Git repository.` with **Remove from recent**. With more than six entries, typing while the list has the keyboard filters it (every word must match the name or path), the count reads `3 of 10`, `Esc` clears, and the list keeps its height. A launch (or Open…) folder that is not a repository adds one amber line above the cards, `<path> is not a Git repository.` (truncating; full path and Git's message on hover) with **Initialize here…**, which opens New repository on it; the footer does not repeat the error. With no recent repositories the title reads **Welcome to Git Good** with *Open a repository to see its history and changes.*, RECENT is absent, and two lines read *Repositories you open are listed here. Drop a folder on this window to open it.* and `Clone folder: <folder> · Change in Preferences…` (opens Preferences › General). Dragging files over the welcome view shows an overlay with a dashed border, `Drop to open <folder>` (`Drop to open` when the platform gives no path); dropping a repository folder, or a file inside one, opens its repository, and any other folder opens New repository on it; an unborn branch reads *No commits yet on <branch>* with **Go to Changes** when there are changes, and the sidebar lists the branch with *no commits*; a filter with no matches reads *No commits match “<text>”* with **Clear filter**; a clean Local Changes replaces the lists, reader, and commit form with *Working tree clean*, the last commit, and one next step (**Pull n** when behind, **Push n** when ahead, otherwise **Open History**; not while amending); an empty Review comparison leaves the file list blank and the reader says *This commit changes no files*, *No differences from HEAD*, or *No changes against parent n* with **Compare with parent m**. Empty sidebar groups keep their header and count with no filler line. History, Review, Local Changes, and diff rows that are not read yet keep their fixed slots empty; the commit details message slot stays empty until the message arrives; an empty Review file list stays blank until its first files arrive (only a finished empty comparison says so); a reader with no content yet, an unread full file, and a file-history reader before its first page stay empty; and the Worktrees, submodule, and LFS windows stay empty during their first read, showing progress only for changes they make (adding or removing a worktree, updating a submodule, fetching an LFS object). The reader's one-line state slot is always reserved and carries only completeness notes and errors, never loading. Endpoint labels show the reference alone (`HEAD`) until its commit is known. Progress for long reads belongs in the status line and the operation area.

Read selected-file content on a worker independent of history indexing. Key results by review generation, comparison, and file. Coalesce requests, cancel obsolete work between batches, and apply current results. Page diff rows and keep every file reachable through bounded caches.

### Changed-file implementation

Walk trees depth-first in Git tree order, skip identical subtrees, and defer blob contents to selected-file requests. The frontier scales with active tree entries. Yield between tree visits; individual tree decoding remains one operation.

Use an independent comparison worker with 32-step/4-ms slices, one request/result slot, temporary record/offset files, 256-row pages, and at most 768 UI rows. Retry replaces the worker and its mailbox for the same pinned comparison, retaining selected path, displayed diff, pixel anchor, and known count while enumeration catches up. Immutable comparison IDs preserve path order. Closing review cancels it; obsolete mailboxes remain isolated.

A line counter runs beside the comparison worker on the same record file and counts added and deleted lines per file like `git diff --numstat`: requested rows first, then every listed file in order, in 8-ms slices. It reads object headers before content and counts only within the text-diff budgets (2 MiB per side, 100,000 combined lines, the 250-ms algorithm deadline); binary content is marked `bin`, while gitlinks, over-budget sides, and unreadable objects stay uncounted. A file/symlink type change counts every line of both sides, as Git splits it into a deletion and an addition. Its mailbox publishes the requested rows' counts and the running total, complete once the listing finished and every listed file is counted; counts wait while a replacement comparison is pending, and a retried comparison keeps its finished total.

Present status/path rows and selected before/after IDs and modes. A persistent Before/After header names the resolved base and target commits; when the comparison is against a ref such as `HEAD`, the ref name is shown with the resolved commit. The commit-row action is **Compare with current HEAD**. The commit identity strip names the selected commit subject only; the shared reader names the selected path and exact endpoints once, so the path and endpoint labels are not repeated above it. Wide layouts show a fixed 300 px file list at the left and the reader in the remaining width. Below 1040 px (narrow proposal) the file list takes the full width over a MESSAGE section (the commit body, or the subject, and `author · date`), and Enter opens a full-width reading view whose one header row starts with **‹ Files** `1/3` (`F` also returns to the list): the endpoints move into the identity row's `vs` picker (`vs parent 73637997`), the change position into the ‹ › tooltips, Blame and File history into ⋯ (`B` and `H` still work), and Prev/Next file give way to `Alt+Up/Down`. The identity row keeps **‹ History** (`Esc` goes back to the caller from both views), the subject, and the ID pill, without the byline. Readers below 1040 px start **Inline** whatever the Default layout; **Side by side** stays available and is remembered for the session. History state and incoming history results wait while review is open; Back restores its caller location and pixel offset before applying current results.

### Diff and layout

Use one selected-file worker with one coalesced request/result slot. Retain one bounded document on the worker; publish at most 256 rows per page and cache at most 768 UI rows. Check blob headers before allocating content. Compare up to 2 MiB per side and 100,000 combined source lines with a 250-ms algorithm deadline. Return an explicit incomplete summary when a budget is exceeded. Cancel before each object header/content read and during row projection; object decoding and the deadline-bound algorithm finish their current operation. Reuse the document for viewport requests.

Use unified diffs with old/new line numbers, fixed-height rows, the window's context lines (3, 5, or 10; default 3, like `git diff -U<n>`), and missing-final-newline markers. The window's whitespace option compares lines by all bytes (default), without whitespace before the line end (`--ignore-space-at-eol`), or without any whitespace (`-w`); rows keep exact bytes, unchanged lines show the new side as Git does, and a file whose only differences are hidden says *Only whitespace changed; whitespace changes are hidden*. The options travel with each diff request; changing them reads the open comparison again as a new generation, centered on the current line. Label byte sizes Before and After. Preserve whitespace/line endings. With **Show invisible characters on changed lines** (default on), added and removed lines draw each tab as `→` and each trailing space as `·` in the weak text color; every marker takes the place of one displayed space, so columns and widths do not move, and context lines and Full file stay plain. Scroll long source lines horizontally in an explicit reading view; with **Wrap long lines** (default off) Diff (both layouts) and Full file instead continue a long line on extra rows of the same fixed height, with the gutter (line numbers, sign, pick box, blame) only on its first row and no sideways scrolling. Text breaks at the last whole monospace column of the reading area, less one spare column, not at word boundaries (`wrap_rows::Wrap` maps display rows to source rows by binary search). East Asian wide and fullwidth characters (CJK ideographs, kana, Hangul, fullwidth forms, most emoji) count as two columns. A character belongs to the row its first column falls in, so a wide character starting in a row's last column stays there and fills the spare column. Row positions come from the column each row's last character starts at, which the diff worker publishes for every row (the character count for text without wide characters), so virtualization, paging, change navigation, and line picking keep working before rows load. The width for sideways scrolling counts wide characters as two as well. Working comparisons always reserve the pick column while wrapping, so picking never reflows text; resizing the window or switching layout, presentation, or side measures again and keeps the top row in view.

**CJK text.** The bundled fonts have no CJK glyphs. The first time egui finds no glyph for a wide character, a system font that has them is read on a background thread: on Linux the first known CJK file under the font folders (`/usr/share/fonts`, `/usr/local/share/fonts`, `~/.local/share/fonts`, `~/.fonts`; Noto Sans Mono CJK first, then Noto Sans CJK, Source Han Sans, WenQuanYi, Droid Sans Fallback), on macOS PingFang, Hiragino or Apple SD Gothic Neo, on Windows Microsoft YaHei, Yu Gothic, Meiryo, MS Gothic or Malgun Gothic. The file is parsed and must draw 漢 before egui sees it, since egui stops on a font it cannot parse. It is appended to both font families after every bundled font, so Latin text keeps its fonts, and the text already laid out is drawn again. One read per run: with no such font the boxes stay (`wide_font.rs`). Distinguish context/additions/deletions with symbols and color.

## History graph and refs · M3

Ref discovery is read-only and shared by CLI and native views. Emit HEAD state (symbolic name, detached flag, commit), local branches, remote branches, and tags with exact short and full names and peeled commit IDs. Skip symbolic remote `HEAD` refs and tags that cannot peel to commits. Keep HEAD explicit for unborn and detached repositories. `git good --cli refs [--repo PATH]` streams this snapshot as JSON; the history worker loads the same snapshot alongside a traversal and replaces it on refresh. History traversal starts from HEAD and every ref target, so branch, remote, and tag-only commits appear in the graph.

Compute graph rows in traversal order, including commits later hidden by a filter, so lane identities stay coherent. The graph column is 56 px (four lanes, as in the History mockup) and widens one lane at a time up to 92 px when a loaded row uses more lanes; it never narrows while the repository stays open, so rows do not shift back and forth. Each row carries its own lane, the set of lanes entering and leaving the row, and parent lanes. Reuse a parent's existing lane, allocate free lanes for additional merge parents, retire empty lanes, and cap layout at 64 lanes. Render stable per-lane colors, vertical continuations, parent joins, commit dots, and a ring for merge commits. A single-parent branch keeps its own lane color until it joins an existing lane; merge parents always use the parent lane color. Only the row's own lane starts a downward segment at the commit; newly created parent lanes are connected by their joins. Cache graph rows with the visible page and evict them with their commits.

Render matching refs as pills before the subject, with tags first, then local branches (the current branch first), then remotes, as in the History mockup; in the dark theme tags are gold and branches blue. Show up to four pills when the subject column has room (two when it is narrow) plus an explicit overflow count. Below 1040 px a branch whose upstream points at the same commit shows one pill, `main ⇄ origin`. Pills are plain text, without a ref-kind icon (kind is shown by color), and keep long labels single-line. Clicking any pill selects its target commit for inspection without moving HEAD. Double-clicking a branch or remote pill other than the current branch switches to it, as double-clicking its sidebar row does (below); tag pills only select.

### Network operations

Clone, fetch, push, and remote-branch checkout are explicit mutations delegated to the Git executable for transport, credential helpers, SSH agents, hooks, configuration, and repository locking. This preserves Git-compatible authentication and protocol behavior while gix remains responsible for discovery and object reads. Locate Git through `PATH`; a missing executable returns installation guidance. Run with an explicit working directory, remove `GIT_DIR` and `GIT_WORK_TREE`, and never invoke a shell.

Ordinary push selects one local branch and one remote without force; a push that would overwrite remote work is rejected by Git and reported as `Push rejected: origin/main has commits you don't have. Other failures, such as a declined remote hook, offer only Details…. The default remote is `origin` when configured, otherwise the sole configured remote, otherwise an error. `--set-upstream` records the pushed branch's upstream only after Git reports success.

**Force push with lease** is a separate, explicit action from the Repository menu. It is enabled only when the current branch has an upstream whose remote-tracking ref exists. The confirmation names the local branch, destination remote/branch, and the lease commit read from the remote-tracking ref; it states that Git rejects the rewrite if the remote branch no longer matches that lease and that bare `--force` is never used. The worker passes that exact expected commit as `--force-with-lease=refs/heads/<remote-branch>:<lease>`; a later fetch cannot silently broaden the confirmation. The CLI resolves the same lease immediately before pushing. A missing or stale lease fails before any remote ref changes, retains the previous display, and does not offer a generic Retry push that would silently become non-force. A successful force push refreshes refs/tracking and reports the lease in the receipt. Its confirmation lists the remote commits it replaces and the local commits pushed in their place (read with `git log` in the background when the dialog opens), and its filled red primary names the count (`Replace 3 remote commits`).

Clone creates a new destination; an existing nonempty destination is rejected by Git and its error is preserved without deleting user files. Enable native clipboard integration for all text inputs. Opening Clone seeds its URL only from recognized clipboard repository URLs: SSH, `git://`, and `file://` URLs, web URLs ending in `.git`, and plain repository paths on known forges (GitHub, GitLab, Bitbucket, Codeberg, Gitea, sourcehut) or hosts named `git.*`, `gitlab.*`, `gitea.*`, or `forgejo.*`. Web pages, issue and pull-request links, and URLs with a query or fragment are ignored. Compose the destination from an absolute parent folder and a single project-name component, defaulting to the clone start folder and the URL slug. The Clone dialog has one **Into folder** control: a choice list of the saved folders (the preferred one checked), the launch folder, **Choose another folder…** (the desktop dialog), and **Manage clone folders…**; **Name** sits beside it, and the target is written once (`Clones into …`). Manual name edits survive URL changes. Repository → Development base folders (the General section of Preferences) manages the saved folders where the user keeps repositories and lets the user mark one as the default. The default is the marked folder, else the first saved folder, else the launch folder. Clone lists the saved folders in order, then the launch folder last, and marks the default with a checkmark. Choosing an entry, typing an absolute folder, or picking one in the desktop dialog sets the clone start folder for the rest of the session; marking a default replaces it, and each launch starts at the default. Persist the ordered list and the marked default under the `clone_folders` key of `gg/settings.json` under the OS configuration directory; an existing `gg/roots.json` is read once when that key is absent. Validate button and Enter submission identically. Every folder field — clone destination, development base folders, repository path, and worktree destination — offers the native folder dialog.

After a successful fetch, reload refs and history while retaining the current selection where possible. After a successful push with upstream changes, reload tracking and refs. After clone, open the new repository only when Git succeeded. A failed or cancelled fetch, push, or remote-branch delete keeps the displayed state and selection and re-reads refs, history, and status in place, because Git may have finished part of it; nothing is rolled back. A cancel reports `<operation> cancelled. Git Good re-read the repository; check what changed before retrying.` (for example `Fetch from origin cancelled. …`), and **Retry fetch** or **Retry push** is enabled once that re-read finishes. Network mutations never run automatically during refresh, launch, or ref navigation.

### Credentials

Use Git's configured credential helpers, SSH agent, and protocol configuration. The native app runs network operations without an interactive terminal and reports a missing-credential failure with the remote name and a pointer to Git credential configuration. CLI operations may use the invoking terminal's normal Git credential prompt. Redact URL user information and never copy credentials, helper output, or raw environment values into receipts, logs, progress, or errors.

### Progress and cancellation

Parse Git's stderr progress as a bounded sequence of phases and percentages. Coalesce updates so the UI repaints at a steady rate, truncate long lines, and never buffer an unbounded transcript. CLI commands emit one final JSON receipt on stdout; progress belongs on stderr and may be suppressed when stderr is not a terminal. **Cancel** sits in the footer beside the network progress; it sends a kill to the Git child, reaps it on the worker, reports cancellation without implying a rollback (`<operation> cancelled. Git may have finished part of it; check what changed before retrying.` from the CLI), and leaves the previous view usable. Network operations are serialized: duplicate Fetch, Push, Clone, or remote-branch checkout actions stay disabled until the worker finishes. The worker waits on Git's progress, not a timer: it notices the exit as soon as Git closes stderr and checks for a cancel request every 15 ms (RULE-16).

Remote-branch checkout creates a local branch that tracks the selected remote branch. It uses the same clean-worktree, validation, `--track`, hook, and post-checkout failure rules as local branch switching; it never detaches HEAD silently.

### CLI

`git good --cli fetch [REMOTE] [--prune] [--repo PATH]` updates remote-tracking refs and prints a JSON receipt with the repository, remote, and fetched state. `git good --cli push [REMOTE] [BRANCH] [--set-upstream] [--force-with-lease] [--repo PATH]` prints the pushed branch, remote, upstream, force-with-lease state, lease commit, and any warning. Bare `--force` is not accepted. `git good --cli clone URL [PATH]` prints the cloned path and resolved repository state. Commands stream progress on stderr and keep stdout parseable. Failures use stderr and a nonzero status without a partial receipt.

Rationale: Git owns protocol and credential compatibility, while Git Good owns explicit selection, bounded progress, cancellation, and a single refresh boundary.

## History mutations and recovery · M5

### Stash

List stash entries from the `refs/stash` reflog through the shared engine: position, full `stash@{n}` reference, recorded commit, and reflog subject. Newest entries come first. An empty stash list is explicit rather than an error. Stash listing is read-only and never changes refs, the index, or working files.

Delegating stash mutations to the Git executable keeps conflict detection, index restoration, and reflog semantics identical to Git. Remove ambient `GIT_DIR` and `GIT_WORK_TREE`, run with an explicit working directory, and never invoke a shell. A reference is accepted only as `stash@{n}` or a bare `n`; option-shaped or non-numeric references are rejected before Git runs.

Push records modified and staged changes, optionally including untracked files and keeping staged content in the index. In the app, **Include untracked files** starts checked ("stash my changes" usually means new files too) and then remembers the last submitted choice; the CLI keeps Git's default and includes them only with `--include-untracked`. A clean worktree is an actionable error, not an empty receipt. Apply and pop restore the selected entry; `--index` also restores staged state. When Git reports conflicts, the operation keeps the stash entry, lists the unmerged paths, and leaves the conflict markers in the worktree. Pop removes the entry only after a conflict-free apply. Drop removes the selected entry after an explicit confirmation and never touches working files.

`git good --cli stash list [--repo PATH]` prints a JSON snapshot with the repository and entries. `git good --cli stash push [-m MESSAGE] [--include-untracked] [--keep-index] [--repo PATH]`, `git good --cli stash apply|pop [STASH] [--index] [--repo PATH]`, and `git good --cli stash drop [STASH] [--repo PATH]` print JSON receipts with the reference, applied/created/dropped state, conflicts, and warnings. Failures use stderr and a nonzero status without a partial receipt.

The native **Changes → Stash changes…** dialog records a message and the untracked/keep-index options and counts what it will stash (`3 files · 2 staged, 1 unstaged`, read in the background and following the untracked option); its primary names the count (`Stash 3 files`, `Enter`). The **Stashes** picker is the one stash surface: **Changes → Stashes…**, the refs sidebar's stash rows, and a footer **Stashes…** recovery open it, and there is no separate Stashes window or Restore dialog. Apply restores and keeps the entry, Pop restores then removes it, and a remembered **Restore staged state** checkbox also restores what was staged; **Drop…** confirms in place with a filled red primary. Successful stash mutations refresh the history, refs, and status boundary so the worktree state stays current. A conflict reports its paths in the status line and keeps the entry for recovery; stash conflicts never grow sequencer controls.

### Merge, cherry-pick, revert, and recovery

Merge, cherry-pick, and revert are explicit mutations delegated to Git so commit order, parent selection, hooks, and conflict behavior match the executable. Each operation validates a clean worktree, resolves one explicit commit or ref, and reports conflicts with unmerged paths instead of manufacturing a result. An in-progress merge, cherry-pick, or revert is detected from the repository state and exposed as Continue, Skip where supported, and Abort. Abort restores the pre-operation HEAD, index, and worktree as far as Git can; failures report detail for manual recovery without deleting user files. Conflict resolution shows base, ours, and theirs content for each unmerged path and marks a path resolved by staging it.

The conflict workspace (`conflict_workspace`) is the Changes view while a merge, rebase, cherry-pick, or revert has conflicted files, in the Final · Rebase conflict layout, under the operation band. The band's **Resolve conflicts** and the Changes tab open it; it has no heading and no Close: `Esc` returns to the plain changes list, and the band's **Resolve conflicts** brings it back. The left pane is 300 px (narrower below 940 px) with 22 px rows: `CONFLICTED n` with each file marked `!` in amber and what is left in it (`2 left`, `ready`, counted on the paths worker), `All conflicts resolved. Continue with Ctrl+Enter.` once none are left, `RESOLVED, STAGED n` with ✓ and **−** (unstage the resolution: `gg_git::conflict::reopen` recreates the conflict with `git checkout -m`, else unstages the path), `ALSO CHANGED BY THIS MERGE` (staged paths that are not conflicted, `~`), and at the bottom the legend (`In a merge, Ours is main, the branch you are on, and Theirs is origin/main, the branch coming in.`; `In a rebase, Ours is the rewritten branch so far and Theirs is the commit being replayed.`). The 28 px file header holds the path (monospace) and its state (`2 conflicts left`, `ready to stage`), then **Block by block** | **Whole file**, **Open in editor**, and **Refresh external edits**. Side labels name the real refs, read by `gg_git::conflict::side_names` on the content worker: `Ours · main (current branch)`, `Theirs · origin/main (being merged)`, `Theirs · 9a4f9a95 (picked commit)`, `Theirs · undo of 7151cc83`, `Ours · rewritten branch (onto main)` and `Theirs · 0f99a42b (replayed commit)`; the stage number and full identity are in the label's tooltip (`Stage 3 · 9a4f9a95 Add login`). The footer reads `1 / 2 / 3 / 4: ours · theirs · ours+theirs · theirs+ours`, `[ ]: previous / next conflict`, `Ctrl+S: stage file`, `Esc: changes list`, and at the right what Abort restores (`Abort restores main to its tip before the merge`, or the rewrite's backup ref).

Text conflicts resolve **Block by block** by default. `gg_git::conflict::blocks` runs `git merge-file -p --diff3` on the file's stages (in a temporary directory, so neither the working file nor `merge.conflictStyle` changes the result) and `gg_engine::conflict::parse_diff3` splits the output into common text and blocks. Each block is a bordered frame (amber until chosen, green once chosen, brighter when current): a header with `Conflict 1/2`, the line where it starts in our version (`line 41`), and **Ours**, **Theirs**, **Ours + theirs**, **Theirs + ours** at the right (the chosen one filled in its side's color), then Base, Ours, and Theirs in three equal columns (Ours tinted blue and Theirs amber when the choice takes them). Each column clips to its own rectangle and wraps its monospace text inside it, so long lines never paint over a neighbour. Keys 1–4 act on the current block (clicking a block makes it current) and move to the next block without a choice; `[` and `]` move to the previous or next block, wrapping; they wait while a text field has focus. The blocks take up to 60% of the height and scroll; the **Result** below gets the rest. The Result is an editable, line-numbered monospace editor holding the working file as it will be staged (`conflict_result`): blocks without a choice keep markers that name the sides (`<<<<<<< main` … `>>>>>>> origin/main`); choosing an option rewrites only that block's region, and hand edits elsewhere are kept; choosing an option for a block already edited by hand asks first (`Replace edited block`). Lines are tinted by origin and stay stable while typing: Ours lines in the Ours tint, Theirs lines in the Theirs tint, unresolved blocks in the warning tint with orange markers, hand edits and common text neutral. `Ctrl+Z` and `Ctrl+Y` undo and redo choices and typing together (typing within a second is one step). **Stage resolution** (`Ctrl+S`, also while typing) is enabled once the Result has no conflict markers left and publishes exactly the Result's text through `publish_text`, which applies the same stage and working-byte revalidation as whole-file publication and keeps our side's executable bit. **Open in editor** opens the selected working file with the editor command from Preferences › General › Editor (`{file}` is replaced by the path, which is otherwise added at the end; quotes group words), or with the system's default app (`xdg-open`, `open`, or `start`) when the command is empty; Git Good does not wait for the editor, and **Refresh external edits** reloads the file. Blocks come from the stages, so the workspace also checks the working file against them: `gg_engine::conflict::edited_outside` reports an edit when the working file has no conflict markers left or its Ours or Theirs text differs from the fresh merge (marker labels, CRLF endings, and the merge, diff3, or zdiff3 style are not edits). An edited file shows `This file was edited outside the conflict blocks.` above the blocks with **Use working file**, which stages the working file as it is, and **Stage resolution** becomes **Replace with blocks…** (`Ctrl+S` too), which asks in a modal (`Replace edited file`, **Cancel** `Esc`, danger **Replace and stage** `Enter`) before overwriting it. Both still revalidate the snapshot, so an edit made after the preview is refused as stale. Binary, oversized, deleted-side, symlink, mode, and submodule conflicts have no blocks; **Block by block** is disabled with the reason and **Whole file** applies.

In **Whole file** mode one source wins outright: a frame headed `Whole file` offers **Take ours**, **Take theirs**, and **Keep working file** (the default, so external edits are inspectable before publication), with each side's size beneath (`12 lines · text`), and the Result shows the chosen source read-only. Choosing never writes or stages anything. **Stage resolution** is the single publication step; it revalidates the conflict stage IDs and exact working bytes captured by the preview, then writes the chosen result and stages the path. A changed stage or working file returns an actionable stale-preview error in the conflict workspace and footer and requires **Refresh external edits**. If the worktree write succeeds but staging fails, the error states that the working file was already replaced; the review path, operation state, and index remain inspectable. Oversized regular working files are validated by exact streaming hash without a text preview; absent, symlink, directory, and submodule worktree paths disable the working-file source with an explicit reason. A delete/modify conflict (exactly one of Ours and Theirs absent) adds **Keep deletion**: the deleted side reads `(deleted on this side)`, choosing that side disables Stage resolution with `This side deleted the file. Choose Keep deletion to stage the removal.`, and Keep deletion previews the consequence (`docs.md will be deleted; the other side's changes to it are discarded.`); Stage resolution then removes the path from the index and the working tree after the same revalidation (`git rm` for that path). Choosing the modified side keeps the file. Stage resolution is disabled while another operation runs or the selected source has no content. Conflict listing, content reads, and resolution publication run on workers; after success the view selects the next unresolved path predictably.

A conflict path is the exact bytes Git lists (`gg_git::conflict::unmerged`), carried unchanged through the content model (`Content.path_bytes`), the workspace's lists, and every resolve, stage, and reopen call; `gg_engine::review::display_path` escapes it only where it is shown. Every Git command Git Good runs on a path the user chose or Git listed treats it as a literal path, never a pathspec pattern: the conflict commands (`checkout --ours|--theirs|-m`, `add`, `rm --cached`, `restore --staged`, `ls-files -u`) and the LFS and submodule reads and update (`ls-files`, `submodule status|update`) run with `--literal-pathspecs`, and Discard all names newly added files as `:(top,literal)<path>`. A file named `*.txt` therefore never selects `a.txt`. Stage, unstage, and discard of single files edit the index through gix by exact path bytes and take no pathspec; `blame` and `ls-tree` take a path, not a pattern; whole-worktree operations keep the deliberate `:/` pathspec.

Merge, rebase, and continue/skip/abort run on one background operation worker, and so do cherry-pick, revert, reset (its hard-reset collision check, backup ref and reset, in that order, as `gg_git::reset::reset` runs them), the stash mutations, branch create, rename and delete, and tag delete. One job runs at a time: `start_operation` refuses a second, and the commands and dialog primaries that would conflict are disabled with `Wait for the current operation to finish`. The footer names the running job with a spinner (`Merging origin/main into main…`, `Stashing 3 files…`, `Restoring stash@{0}…`, `Deleting branch merged…`, `Resetting to 1a2b3c4…`, `Cherry-picking 1a2b3c4…`) and the band names a running continuation. The Merge, Rebase and Reset dialogs and the Stashes picker close as the job starts and report failures in the footer; Stash changes, New branch, Rename, Delete branch and Delete tag stay open with their primary disabled until Git returns, close on success, and show a failure in place (`OperationOwner` routes it; a dialog closed meanwhile leaves the failure to the footer). Confirmations revalidate before the job starts (RULE-05). Each result publishes the receipt its synchronous form published and starts the same refreshes: history, refs, status, reflog and backups as before for each mutation, once; failure clears the pending label and reports the error while preserving Git's recovery state.

## History rewrites and recovery · M6

### Amend

Amend rewrites the latest commit with the current index and an edited message. It requires an existing HEAD and a working tree, validates the repository status, pins the previous HEAD, and preserves the previous commit's author and parents. The committer identity and time come from the current configuration. An empty index is valid for a message-only amend; unlike a normal commit, the tree may equal the old tree.

Amend mode compares the index with the parent of HEAD rather than with HEAD. `StatusIdentity.base_tree` pins that parent tree (the empty tree for a root commit), and `Session::open_amend`, `working_diff`, and `unstage` use it as the before side. The staged rows therefore describe the proposed commit contents: existing changes in HEAD remain visible, newly staged working changes join them, and unstaging a file, hunk, or line restores the parent side in the index. Staging still compares the index with the working tree. Working files are never modified by staging or unstaging, and the usual index-lock, stale-observation, conflict, and whole-file mode checks apply.

Run `pre-commit`, `prepare-commit-msg` with the message file, `commit` source, and the old commit ID, then `commit-msg`. Re-read the message and index afterwards, reject a HEAD change made by a hook, acquire the index lock, rebuild the tree, and write the commit object with the original parents. Update `HEAD` atomically with the observed old ID as the expected value and write a `commit (amend): subject` reflog entry. Run `post-commit` and `post-rewrite amend` after publication; their failures are warnings because the rewrite already exists. `post-rewrite` receives the old and new IDs on stdin through `git hook run --to-stdin`, because the hook runner does not forward the parent process's stdin.

Before publication, create `refs/gg/backup/<label>/<unix-nanos>/<branch>` (no branch segment on a detached HEAD) pointing at the previous tip, so the backup records the rewritten branch and when it was saved. A backup failure aborts the rewrite. Backup refs are private recovery anchors: the refs snapshot excludes `refs/gg/`, so they never appear in the sidebar or graph labels. The amend receipt carries `amended`, `previous`, and `backup` in addition to the commit, tree, parents, and warnings. CLI `git good --cli commit --amend -m MESSAGE` prints the same receipt.

The Local Changes commit/amend form sits below the reader: at the lower right in wide layouts and below the reader at narrow widths, so it remains available while reading a comparison. Below 1040 px the form has no **Sign** checkbox (signing follows Preferences › Commit › Sign commits) and no **Expand**: its message box fills a panel resized by dragging the panel's top edge, up to 60% of the height. It exposes an **Amend HEAD** toggle; the message field's placeholder reads *Commit message (first line is the subject)*, and the button's tooltip names its shortcut (`Ctrl+Enter`, or `Ctrl+Shift+Enter` when amending). The change groups are headed `UNSTAGED <n>` and `STAGED <n>`, with **Stage all** and **Unstage all** at the right of their headers (the same commands as the Changes menu). A hovered or selected row shows a **+** (stage) or **−** (unstage) button in a fixed slot at its right edge; conflicted and intent-to-add rows have none. With a list focused, `S` stages the selected Unstaged file and `U` unstages the selected Staged file. **Several files** are picked within one list: Ctrl/Cmd-click adds or removes a row (the first one keeps the file already selected), and Shift-click or `Shift+Up/Down` selects the rows from the anchor (the last row clicked without Shift) to the clicked or moved-to row; picking in the other list starts over there. Picked rows share the selection fill, the reader shows the last one clicked, and the status line starts with `N files selected`. A range reaching rows no page holds is read whole by the status worker from its disk store once the scan completes, and acts only then (*Still reading the selected files.*). With two or more picked, `S`/`U`, a row's **+**/**−** on a picked row, the reader's whole-file **Stage**/**Unstage**, and **Discard file…** act on all of them as one mutation that checks each file against the status it was listed in and reads the identity again after it (*Discard unstaged changes from N selected files? The index is unchanged.*); files that cannot take the action (conflicts, intent-to-add) are skipped, and a plain click, or an action, ends the selection. `Ctrl/Cmd+C` copies the picked paths, one per line. The status line follows its summary with the mockup's hints (`S / U: stage / unstage · [ ]: hunks · Ctrl+Enter: commit`); refresh is automatic, so the old Refresh button is gone and **Retry** appears in its slot only after an error. Review's file list shows `Esc: history · Up/Down: files · [ ]: changes · Alt+Left/Right: versions · H: file history · B: blame`. Unstage all is disabled while amending, because it resets the index to HEAD while Staged shows HEAD's parent. Enabling it loads the current HEAD message without replacing a nonempty amend draft, keeps the normal draft separate, restarts status against HEAD's parent, and shows a banner above the form that names the affected commit and subject, names the amend base (its parent or a root/empty tree), and explains that staged changes are the commit contents. The action becomes **Amend HEAD**; the same reader provides the header **Stage** and **Unstage** button, plus hunk and line stage/unstage actions on the active comparison. Unstage in amend mode removes the selected change from the amended commit and leaves working files unchanged. After success the toggle and amend base clear, the status line reads **Amended HEAD → \<id\> · N files**, the remaining normal draft is retained, and the lists refresh against the new HEAD.

### Reflog

Read reflog entries through `git reflog show --date=unix --format=%H%x00%gD%x00%gs%x00%s REF`, with `HEAD` as the default. Parse the timestamp from the dated selector, reconstruct stable `REF@{n}` index selectors from entry order, split the reflog subject at the first colon into an action and detail, and keep the recorded commit's own subject. Missing refs, option-shaped references, and Git failures return actionable errors; listing is read-only and never changes refs, the index, or working files. `git good --cli reflog [REF] [--repo PATH]` prints the repository, reference, and entries as JSON.

The native **Repository → Recovery…** window (`recovery_view`), the single entry point for backups and the reflog, follows the inspect proposal. Its header holds the title, a **Backups <n> | Reflog** switch, and, for the reflog, a **Reference** choice of `HEAD` and the local branches in 24 px menu rows (✓ column, `current` at the right of the checked-out branch). Each source is a 22 px table with the time first: Backups lists SAVED (relative), BRANCH (a pill), BEFORE (rebase, amend, rewrite, reset, restore), TIP, and SUBJECT under the line *Saved by Git Good before each rebase, amend, rewrite or reset. Hidden from the refs sidebar.*; Reflog lists WHEN, ENTRY (`@{n}`), WHAT HAPPENED, and COMMIT, with Git's wording translated into plain events (*Finished rebase of feature/x*, *Rebase picked “Add footer notice”*, *Switched from main to feature/x*). The selected entry is a label grid: TIP or COMMIT (8-character ID, subject, copy button); SAVED (date and time · *before rebase of <branch>*) or WHEN (date and time · relative); BRANCH NOW (the branch tip and how many commits differ from the backup); REF or ENTRY (with a copy button); and GIT MESSAGE (the raw reflog subject). The footer holds **Delete backup…** (Backups only) and **⋯** at the left, then **Open commit**, **Create branch here…**, and the filled primary **Restore <branch>…** (`Enter`; *Restore <branch> here…* for the reflog). **⋯** holds Copy commit ID (`Ctrl+C`), Copy ref (`Ctrl+Shift+C`), Reset branch here ▸ Soft *keep index and files* / Mixed *keep files* / Hard… *discard changes*, and Delete backup… (`Del`, Backups only). Results and read errors appear in the window's 22 px status strip, which otherwise counts the backups or names the entries and reference. Empty sources say what fills them (*No rewrite backups yet. Git Good saves one before every rebase, amend, rewrite or reset.*, *No reflog entries for <ref>.*). There is no Refresh button: the window re-reads on open, when Git Good gets focus back, and after every operation, on a background thread, keeping its row heights while the read runs. The selection is kept by backup reference or reflog selector, so a return location selects its entry once the list arrives. Its default width and maximum resize stay inside the available viewport, including 720×480, with no clipped controls. **Open commit** runs the ordinary commit review and records the recovery source, the Reflog reference, and the selected entry as its return location; Back returns there. Reset ▸ mode reuses the existing reset path and confirmation, including the Hard warning that staged and working changes are discarded. Create branch resolves the selected commit, validates the name, rejects an existing branch, and uses the shared form with **Switch after creation** off; the current branch and worktree stay put. Successful restore, reset, deletion, and branch creation refresh refs, history, status, and the open Recovery source.

**Restore <branch>…** (`gg_git::backup::restore`) is one confirmed action instead of a reset mode: a hard reset of the checked-out branch to the selected commit that needs a clean tree and first saves the current tip as a `restore` backup, so it can be undone. The confirmation reads *Move <branch> from <tip> back to <id> <subject>?* with *Files are checked out to match the backup.* and *The current tip <tip> is saved as a new backup, so this can be undone.*, then Cancel `Esc` and **Restore branch** `Enter`. When it cannot run, the footer's left names why and the primary stays disabled: *<n> files have uncommitted changes. Commit or stash them first.* (tracked files with staged or unstaged changes), *<branch> is not checked out. Switch to it first.*, or *Check out a branch first.* A hard reset that would overwrite untracked files is refused as before. **Delete backup…** confirms with the branch, commit, and subject, then removes only that `refs/gg/backup/` reference (`gg_git::backup::delete` refuses any other reference); backups otherwise expire only under **Keep private backups**.

### Rebase

`git good --cli rebase REF [--autostash] [--repo PATH]` rebases the current branch onto one explicit local branch, remote-tracking ref, or tag. The reference is resolved to a commit before any mutation. A tracked working tree must be clean; `--autostash` is the explicit opt-in for working changes. The backend always passes `--autostash` or `--no-autostash`, so repository configuration cannot silently change the decision. Untracked files do not block the clean check; Git still refuses a rebase that would overwrite one. An operation already recorded by Git must be recovered before another rebase starts.

Before Git runs, pin the current HEAD and create `refs/gg/backup/rebase/<unix-nanos>` pointing at it. A backup failure aborts the rewrite. The rebase itself runs through Git with non-interactive editors so commit order, hook behavior, and conflict semantics match the executable. The receipt carries `reference`, resolved `commit`, `previous`, `backup`, `applied`, `in_progress`, `conflicts`, and `warnings`.

An in-progress rebase is detected through `rebase-merge` or `rebase-apply`, with the commit being applied read from `REBASE_HEAD`. The operation band names the rebase and exposes **Continue**, **Skip commit**, and **Abort and restore**; the conflict workspace lists unmerged paths, and **Recovery…** remains in Repository and in the outcome recovery action. Continued and aborted rebases refresh history, refs, status, an open reflog, and open backups, and restore the pre-rewrite history row. `git good --cli rebase --continue|--skip|--abort [--repo PATH]` prints the same receipt shape with null reference, commit, previous, and backup fields.

The native **Branch → Rebase current onto…** action and each branch, remote, and tag context menu open a confirmed **Rebase branch** dialog with a reference field and an **Automatically stash working changes** option. The dialog states that the rewrite creates a private backup ref. Ref actions are disabled while a mutation is in progress.

### Preferences

**Repository › Preferences…** (`Ctrl/Cmd+,`, also in search) opens a modal, fixed-size window (title row with ×, footer naming the settings file with **Close**; Esc or a click outside also closes it); **Development base folders…** and Clone's **Folders…** open it on General. Sections are listed on the left and the selected one scrolls on the right. Changes apply at once and are saved immediately; a save failure is shown in the window. ### Interactive rebase

`git good --cli rewrite --from COMMIT [--autostash] STEP... [--repo PATH]` rewrites the linear range from the named commit through HEAD. A step is `--pick`, `--edit`, `--squash`, `--fixup`, or `--drop COMMIT`, or `--reword COMMIT MESSAGE`, in todo order (oldest first). The start commit is resolved and checked as a HEAD ancestor. The range is listed oldest first and must be linear; merge commits are rejected rather than flattened. Every range commit must appear exactly once in the ordered steps.

The engine plan (`gg_engine::rewrite::Step`) has six actions:

- **pick** keeps the commit.
- **reword** keeps the commit with the step's new message, stored as given apart from whitespace cleanup (`#` lines are kept). The message must not be empty, and only reword steps carry one.
- **edit** (shown as **Reopen**) picks the commit, then stops with its changes staged on its parent, so they can be committed again whole or in parts before **Continue**. The todo line is `pick` followed by an `exec` script that writes `<git-dir>/rebase-merge/gg-reopen` (the parent, then the original commit), runs `git reset --soft HEAD~1`, and exits non-zero so Git always stops there; `--no-reschedule-failed-exec` keeps Continue from running it again. A root commit has no parent, so it stays at HEAD to be amended. The receipt reports `in_progress` without conflicts and a warning naming the reopened commit.
- **squash** combines the commit into the nearest kept commit before it and joins both messages; **fixup** does the same and keeps only the older message. Both are refused when no kept (non-dropped) commit precedes them.
- **drop** leaves the commit out. Dropping every commit is refused with a pointer to Reset.

The CLI receipt carries `from`, `previous`, `backup`, `applied`, `in_progress`, `conflicts`, `warnings`, and the step count.

The backend writes the whole interactive-rebase todo to `<git-dir>/gg-rewrite/todo` and installs it with `GIT_SEQUENCE_EDITOR=cp '<todo>'`, shell-quoted. A reword becomes `pick` followed by `exec git commit --amend --only --allow-empty --cleanup=whitespace -F '<message file>'`, so no interactive editor runs and commit hooks apply as they do for Git's own reword; a failing hook stops the rewrite and the receipt carries Git's output as a warning. The plan directory is replaced on every rewrite. `GIT_EDITOR=true` accepts the combined squash message, and `--no-autosquash` and `--no-rebase-merges` keep repository configuration from changing the plan. A root range uses `--root`; a shallow boundary is rejected rather than rewritten as a root. A tracked working tree must be clean unless `--autostash` is explicit, and `--autostash` or `--no-autostash` is always passed. Before Git runs, create `refs/gg/backup/rewrite/<unix-nanos>` pointing at HEAD; a backup failure aborts the rewrite.

`gg_git::mutation::rebase_progress` reads an interactive rebase in progress from `rebase-merge`: the done and remaining commit-bearing todo lines with full IDs and subjects, the branch from `head-name`, the count of changed tracked files, and the stop: **Conflict** (unmerged paths), **Reopened** (Git Good's reopen script was the last line run; carries the base, the original commit and message, and the commits made since the stop), or **Other**. The frame's background summary reads it on load, focus, Local Changes refresh, after a commit, and after each operation.

While a rebase is stopped, the operation band (the template the other operations follow) names the stop and step on its first line (`Rebase stopped · step <n> of <total> · reopened <id>`, `Conflict · step <n> of <total> · applying <id> <subject>`, or `Rebase stopped · step <n> of <total> · after <id>`, with 8-character IDs), and holds **Resolve conflicts** (the filled primary while conflicts remain and the workspace is closed), **Continue** (`Ctrl/Cmd+Enter` when no text field has focus), **Skip commit**, and **Abort and restore**. Continue stays disabled until conflicts are staged and, at a reopened commit, until no tracked changes remain; the reason is the band's status, at normal size right after the title (`Resolve and stage 1 conflicted file first.`), and the title truncates first. Once it can run, Continue is the filled primary. The second line explains what to do, followed by step chips, each the step's 8-character ID and action as in the mockup (`✓ 0f99a42b pick`; done with a check, the current step highlighted, the next steps; the subject on hover), collapsing as described for the band. A reopened commit also lists **Commits made at this stop**. Local Changes lists them too, as in the stop mockup: under the STAGED list (wide layout), a `COMMITS MADE AT THIS STOP` section shows each commit's 8-character ID and subject. The band is purple (pause glyph) at a reopened or paused step and amber (warning glyph) at a conflict, with bordered step chips (the current one filled in the band's color); **Continue** carries its `Ctrl+Enter` hint (muted until ready, the filled blue primary once it can run) and **Abort and restore** is red. The window identity names the rebase step; the branch button keeps the branch's name followed by `rebasing <n>/<total>` or `conflict <n>/<total>` in the band's color, in place of the ahead/behind counts. A newly reopened commit opens Local Changes once with its original message in an empty commit box; a root commit opens in amend mode. At a reopened step the current chip reads `reopen`, and the commit button says what it makes, filled once it can run: **Amend reopened commit** (*Commits everything staged.*), **Commit staged part** while unstaged files remain (*Unstaged files stay for the next commit.*), or **Commit last part** after commits were made at the stop; the footer names the rewrite's backup ref when Git Good started the rewrite.

Interactive rebase uses the same Git rebase state and operation band as rebase. Conflicts are read from the worktree and `REBASE_HEAD`, with **Continue**, **Skip**, and **Abort** backed by `git rebase --continue|--skip|--abort`. `git good --cli rewrite --continue|--skip|--abort` exposes the same actions. Completion, skip, and abort refresh history, refs, status, an open reflog, and open backups, and restore the pre-rewrite history row.

**Commit › Interactive rebase from here…** (`R` in History, and the commit-row context menu) starts at the selected commit; **Branch › Interactive rebase of current branch…** starts at the branch's first own commit. Both open one large modal (`rebase_dialog`) over the current view; the plan rules live in `rebase_plan` and are tested without a window.

- **Header:** **Interactive rebase**, the branch, the result count (`6 commits → 4 · 1 dropped · 1 stop`), the range (`<from>…HEAD onto <base>`, or *the root*), **Cancel** (`Esc`), and **Start rebase** (`Ctrl/Cmd+Enter`). Start is disabled with the first reason the plan cannot run: unchanged plan, a squash or fixup with nothing to combine into, an empty reword message, every commit dropped, or a rewrite already running.
- **Plan (left), newest first like History:** the header reads `PLAN · NEWEST FIRST, LIKE HISTORY` with the key hint `j k select · Alt+↑↓ move · P R E S F D`; squash and fixup rows are indented 12 px under the commit they join; the last row names the commit the plan is replayed onto (`d699f49 base · unchanged`, or *the root*), and a line under the list reads `Keys on the selected row: P pick · R reword · E reopen · S squash · F fixup · D drop`; each row has a drag handle, move up/down buttons (`Alt+Up/Down`), the short ID (hover names the full ID and refs), branch and tag pills when they fit, the subject (struck through when dropped, dimmed when combined), a consequence badge (`↓ squash into <id>`, `↓ fixup into <id>`, `absorbs <ids>`, `⏸ stops here · reopens staged in Changes`, `dropped · recoverable from the backup`), and an action chip. The chip opens a menu of all six actions with a hint and key; unavailable actions stay listed, disabled with the reason. Keys on the selected row: Up/Down or `j/k` select, **P** pick, **R** reword, **E** reopen (`edit`), **S** squash, **F** fixup, **D** drop. Letters wait while the message field has focus. Squash and fixup combine into the nearest kept commit below (older); the oldest kept commit cannot be combined, and the last kept commit cannot be dropped. Badge arrows and the pause mark are Phosphor glyphs.
- **Selected commit (right):** short ID, action, author, and relative date. Reword focuses an editable message seeded with the original, and shows the original subject below it; other actions show the full message. The commit's files and diff appear in an embedded Review (files above the shared reader, no Back button, identity, or status line). Drop dims the reader and says the changes leave the branch. **Open in Review** (`Enter`) holds the dialog and opens the ordinary Review with **‹ Rebase**; leaving Review by any route returns to the same plan.
- **Footer:** **Stash working changes first** (autostash), the other branches and tags that stay on the original commits, and the private-backup notice. Merge commits are rejected with the reason.

The range listing carries each commit's author, relative date, and full message (`gg_git::rewrite::plan_range`, which also returns the replay base). Debug builds open the dialog with `GG_REBASE=<commit>`.

The native rewrite runs on a background worker. Accepted submission closes the configuration immediately; the operation band reports `Rewriting <branch> · step <n> of <m> · picking <id>` with the step strip (the plan until Git's todo is readable, then Git's own steps), the footer names the backup as soon as it exists (`Backup: refs/gg/backup/…`), and there is no cancel while Git writes. Then the band reads `Refreshing history…` until the replacement history update for the refresh generation is accepted, and the footer shows `Rewrote 4 commits · backup <ref>` with the follow-up action and **Details…**. Browsing stays available, incompatible mutations remain disabled, and the retained pre-rewrite rows are labeled while refreshing. The replacement is adopted when it arrives, anchored to the same commit, so the viewport does not jump.

### Backups and recovery

`gg_git::backup::list` reads `refs/gg/backup/*` with `git for-each-ref`, newest first by the creation time in the reference name, with the label, the rewritten branch (when the name records one), the save time, the commit, and its subject. The refs snapshot still excludes `refs/gg/`, so backups never appear as graph labels or ordinary ref rows. **Repository → Recovery…** (Backups source) and the outcome recovery action after a rewrite open the same Recovery window described under [Reflog](#reflog); its actions never delete user files, and only **Delete backup…** deletes a backup ref.

## File reading and history · M7

### Reading surface

The selected-file view has one file identity and three navigation axes: change, file, and commit. **Diff** and **Full file** are two presentations of the same selected file, not separate viewers. Switching presentation keeps the exact path bytes, the Before/After side, and the reading position. The Before/After side applies to full-file reading; the unified diff always shows both sides.

Read one full-file side on the same selected-file worker as the diff, keyed by generation and side. Reuse the diff document for changed-line markers so a mode or side change never recomputes the comparison. Check the blob header before allocating, refuse sides above 2 MiB, and split at most 100,000 source lines. Missing sides, binary content, gitlinks, symlinks, and budget limits return explicit summaries instead of empty text. Cancel before object reads and between projection steps; a superseded generation or side is never published.

Full-file rows are fixed-height and virtualized with exact one-based line numbers. Added lines on the After side and deleted lines on the Before side carry a marker and the same semantic colors as the diff. Clicking a row sets the cursor; Shift-click extends the range. `Up`/`Down` and `j/k` move the cursor, `Shift+Up/Down` extends the range, `PgUp/PgDn` moves by a page, and every movement keeps the cursor visible. The cursor and range are the place used by history.

**Changed words.** In Diff mode, inline and side by side, each deleted line is paired in order with an added line of the same block (the deleted lines, then the added lines, between unchanged rows), and the words that differ between the two are painted behind the text in a stronger tint of the line's color. Lines are split into words, whitespace runs and single other characters and compared token by token; adjacent changed tokens join into one range. A pair is skipped when either line is longer than 1,000 characters or 400 tokens, and when the two share no word, so a line rewritten throughout keeps only its line color. The reader worker computes this with each published page, at most 256 pairs per page, reading a block that reaches past the page whole so a line's emphasis is the same on every page; the view keeps the ranges per row until another document arrives. Full file and the find highlights are unaffected; find marks paint over the emphasis.

**Find in file.** `Ctrl/Cmd+F` in the reader (Diff or Full file, not image or binary readers) opens a find bar under the header: a field (*Find in file*), the count (`3 of 12`, `10000+` past the limit, `…` while the answer for a new query is on its way, *No matches*), **Aa** (match case) and **W** (whole words: no letter, digit or `_` on either side), ↑ and ↓, and ×. Enter and Shift+Enter, in the field, go to the next and previous match, wrapping, and keep the field focused; Esc or × closes the bar. Every match is highlighted behind its text, the current one more strongly, and going to a match makes its row the place (Full file selects the line; Diff scrolls to the row). The reader worker searches the whole document once per document, mode, side and query, over every row and not just the pages shown (diff hunk headers are not searched), and sends the matches as character ranges of each row, so they fit wrapped segments and invisible-character markers alike; case-insensitive matching compares lowercased characters one for one. A new answer goes to the first match at or after the place; highlights for another document or query are not drawn.

`[` and `]` move to the previous or next change. In full-file mode a change is a contiguous run of marked lines; in diff mode it is a hunk. Visible **Prev change**/**Next change** buttons perform the same actions, name the current change and total, and stay disabled when the file has no changes. Jumping to a hunk requests the page that contains it from the retained diff document rather than scanning loaded rows.

The back pill reads `‹ History` (or `‹ Files`, `‹ Recovery`, `‹ Rebase`) with a dimmed `Esc`. The Review header names the commit as in the Review mockup: the subject (13.5 px, truncated first), the 8-character ID in a pill, and `author · YYYY-MM-DD` from the comparison. At the right, **Compare with** lists the commit's parent(s) (`parent 7c26d684`, or `parent 2 …` for merges) and **HEAD**; choosing one reloads the comparison in place, and the parents stay listed while comparing with HEAD. Debug builds open a commit in Review with `GG_REVIEW=<commit>`.

`Alt+Up` and `Alt+Down` change the selected file while staying in the reading view. The review header exposes **Prev file**/**Next file** for the same action. The selected file, presentation, and side survive the move; the line position is restored when the new file has that line and clamped otherwise. `Esc` still returns to the file list, and `Enter` opens the selected file.

The place is `{ path bytes, revision, start_line, end_line }`, with one-based inclusive lines and exact path bytes. Engine `Place` stores that identity so path, blame, and line history all use one anchor. A deleted range keeps the before side explicit; history must not silently discard it.

### Shared reader

One reader owns the displayed comparison identity, exact path, both endpoint labels, presentation, inspection side, cursor, anchor, and pixel offset across commit review, staging, and file history. The concrete renderer is the existing `DiffView`; `reader::ReaderContext` is the value consumers exchange. Endpoint labels name the resolved sides (`main (a1b2c3d)`, the parent commit, `Empty tree`, or an older content version) and are shown in the reader header together with the exact modes and blob IDs.

Requested and displayed identities stay separate. A new path, side, mode, or source request increments the generation and cancels superseded work; metadata and rows are adopted together only for the matching identity, and endpoint labels appear only when the displayed content matches that identity. `reader::Capabilities` reports what the current comparison actually supports for Diff, full-side selection, and export, so a label never grants an action. Presentation and side controls never change the comparison; changing the comparison never silently changes the file.

`DiffView::save_context` captures the requested identity, endpoint labels, and place, and `open_context` restores them without creating a second viewer. A restored place survives the asynchronous adoption of the matching content, including an identity change. Commit review saves the context when file history changes the comparison source and restores it exactly once when history closes. The same value is the integration point for staging and later history migration; line/range history mapping remains a separate extension point.

### File and line history

History is a cursor over **content versions**, not over commits. A version is one content state of the followed path; commits that carry an unchanged state are skipped, so the timeline never shows a row that changed nothing. The newest version is the content state the selected revision carries, which may have been introduced by an older commit than the one the review opened. **Full file** shows the current version alone; **Diff** shows the edge `previous → current`. The Before/After inspection sides remain a separate reader control and never navigate versions.

History is a comparison-source mode inside the existing Review reader, not a second content view. Opening it keeps the review state and replaces the changed-file list with a scrollable **version list** in the same pane (at the left when wide, a seven-row pane above the reader below 1040 px; `file_history_view`). `H` and the visible **History** button open it for the selected path and place; **History** stays pressed while it is open and a second click closes it. The list header reads `FILE HISTORY 12+` (`+` while more may load) or, for line history, `LINE HISTORY 41–46`, with × (`Esc`) at the right; boundary reasons and Git's notes are its tooltip. Rows are 22 px: kind symbol in its colour · short ID (mono) · subject, a rename adding `← old path` · `MM-DD`, with the full kind, subject, author, and date on hover. The selected row is the comparison's metadata, so there is no separate version line or counter. Clicking a row selects that version; the list scrolls to keep the selection visible. Pages load as the list scrolls: the slot after the last version stays blank until the page arrives (never loading text), and a failed page becomes one red row, `History page failed · <error>`, with **Retry**.

Opening history captures the entry comparison, exact path, revision, presentation, inspection side, cursor/range, and pixel place. Closing history with its button or `Back`/`Escape` restores that context exactly once. Version steps never add navigation or Back history: they change the reader source only. Selecting another file while history is active keeps history open but resets the version cursor to that file's newest content version; the original entry file, comparison, place, and revision stay saved for Close history. Closing returns to that saved entry context and selected file. The previous path's version cursor is never reused. Switching parents leaves history because the comparison revision changed.

Both version directions never wrap: at a boundary `Alt+Left` (older) and `Alt+Right` (newer) do nothing and the header tooltip names the reason — `Oldest version`, `Newest version`, `Only version`, a pending page, a history limit, or a pending predecessor choice. A pending page is a distinct reason from absent: a temporary wait must not read as the end of history.

Predecessor resolution follows carriers of the current content state backwards through parents. If exactly one parent carries the state, the edge is unique and history follows it silently. If several parents carry it and none is a same-state carrier of another, the predecessors are genuinely ambiguous: history stops and nests the candidates under the merge row as ordinary 22 px list rows after a `CHOOSE EARLIER VERSION n` label: kind · short ID · subject and `← old path` · author's first name and date. Up/Down move between them and Enter (or a click) picks one. It never silently takes the first parent. The choice is file-level and becomes the version's edge; choosing a place or hunk inside that edge is a separate question. An edge whose earlier side is not resolved renders the current Full file only, with Diff disabled rather than comparing a file with itself.

A rename is a path-changing edge: the newer version names the new path and the edge names the old path. An absent version is explicit — deletion is a version with no content, not an empty file, and re-adding starts a new added edge. Type changes, additions, deletions, renames, and content changes keep distinct labels. When the trace hits its commit budget, the boundary reports the limit instead of pretending the path starts there.

History preloads a bounded number of versions and pages older ones on demand. The timeline and every version's blob read run on workers keyed by generation; opening another file, backing out, or a newer request cancels the previous work, and a superseded result is never published. A failed page keeps the loaded versions and the pending boundary so a retry resumes rather than restarting. History and blame never move `HEAD`, write refs, or change the index or working files.

`Esc`/`Back` dismisses the active chooser or history source first, then the reading view, then the file list and review, while editor and menu keys retain ownership. `H` while history is open does not stack another history source. Line and range history reuse the same timeline anchored to `Place`. A single line maps through blame first; range boundaries map through diff hunks. When a range spans hunks that diverge into different predecessors, the range asks which predecessor to follow instead of inventing one boundary. A deleted range keeps the before side explicit, and absent versions are identified rather than replaced with empty content. `B` opens blame.

The reader's mode row follows the mockup, in one row: Diff · Full file · Inline · Side by side · **Blame** · **History** · ‹ › · ⋯. **Blame** (`B`) toggles attribution in Full file and, from Diff, opens Full file with blame on; **Blame** always reads Blame and is drawn pressed while attribution is on. **History** (`H`) follows the file's history (Review shows it on this row, or in ⋯ below 1040 px, where **Blame** moves there too; `B` and `H` still work); change navigation uses ‹ › (`[` and `]`); the ⋯ menu ends the row. There is no Stage button in the reader header: whole-file staging stays on the file row's + / − button. ⋯ draws 24 px menu rows with the check column: **Open in editor** (the working copy with the editor from Preferences, or the system's default app), **Reveal in folder** (the folder holding the working file), **Copy path**; **Export before…**, **Export after…**; the **File details** toggle (✓ when on; an opt-in 22 px mono row under the header, off by default and kept across files) and **LFS details…** / **Submodule details…** when they apply; then, after a separator, **Discard file…** last in red (the whole-file discard of unstaged changes). A missing working file reports in the footer.

A segmented **Inline | Side by side** control follows **Diff | Full file** and chooses the Diff layout; **View → Inline diff** and **Side-by-side diff** set the same value, checked for the current layout. The layout belongs to the window (every reader follows it, seeded from the `diff_layout` preference) and is remembered. In Full file the control keeps its slot, disabled with *Full file shows one side; choose Diff to compare*. Side by side shows Before on the left and After on the right, each with its own line number and sign columns; removed lines are tinted red on the left and added lines green on the right. Within a contiguous change, the k-th removed line sits beside the k-th added line and the shorter side is padded with empty cells; context lines appear in both columns, and hunk headers and no-newline notes span both. The diff worker derives the pairing (`split_rows::Layout`) once per document as a list of change runs, so display rows map to unified rows by binary search and rows stay virtualized and paged exactly as inline. Switching layouts keeps the top row in view. Change navigation, keyboard scrolling, the cursor, hunk **Stage/Unstage/Discard hunk** buttons, and changed-line selection for partial staging (click the removed or added cell) work in both layouts. Both columns share one horizontal text offset driven by sideways scrolling (Shift+wheel or a trackpad swipe) instead of a horizontal scroll bar.

Attribution reads one committed path and revision through `git blame --line-porcelain`, with an optional one-based inclusive line range. It is bounded to 2 MiB and 100,000 source lines, refuses binary content, gitlinks, and symlinks rather than pretending to attribute them, and runs on a cancellable generation-keyed worker. It never reads working-tree content; Local Changes disables attribution with that reason. In Full file on either side, **Blame** adds a 184 px gutter and `B` toggles it; the After side uses the selected commit and the Before side uses the parent or against revision. Runs of lines from one commit collapse to one label on the run's first line — author, short ID (mono), and a compact age (`5d`, `3w`) — with a rule above each run, and every line carries a 3 px age bar whose colour is brighter for newer commits (scaled between the oldest and newest commit in view; `blame_view`). The selected line's commit sits in one 26 px metadata bar at the reader bottom: `LINE 42` (or `LINES 41–46`), author · short ID · `5 days ago` · subject, then **Open commit** and **Line history**; with no line selected it reads *Select a line to see the commit that last changed it*, and its height never changes. **Open commit** hands that commit to the ordinary review while preserving the caller return location, and **Line history** opens the existing version timeline anchored to the selected line or range. `git good --cli blame PATH [--revision REF] [--lines START,END] [--repo PATH]` prints the same bounded result as JSON.

Line history maps the selected range through each content edge on a cancellable worker. Context lines map to the adjacent version; a line or range introduced by the newer version stops with **Line introduced in this version**; a line or range deleted in the newer version stops with **Line absent in this version**. A range that contains either is reported whole rather than silently shrunk. Opening from the Before side starts the cursor at that older content version, so a deleted line keeps its Before anchor and its Newer edge reports the deletion. An ambiguous file edge uses the existing predecessor chooser before any range mapping; a range is never split across candidates or given an invented common boundary.

### Worktrees

`git worktree list --porcelain -z` is the read-only inventory. Each row names the exact path bytes, short branch or detached/bare state, HEAD, current/main flags, lock and prunable reasons, and dirty status from a bounded `status --porcelain` read in that worktree. **Repository → Worktrees…** opens a non-modal window in the inspect style, like Submodules: a header with the title and the count, then a 22 px table of BRANCH (`· main worktree` after the main one), PATH (`~` for the home folder, cut from the start with `…` so the worktree's own folder stays visible; the full path on hover), STATUS as a pill (blue Current, green Clean, amber Modified, red Missing, grey Locked and Unavailable) and HEAD (8 characters), in Git's order with missing worktrees last. Under it a label grid shows the selected row's PATH (full, with a copy button), HEAD (`id · subject · author · date` when History has the commit) and STATE (*Main worktree · shown now · no local changes*, *locked: on usb disk*, *folder missing: gitdir file points to non-existent location*). The footer holds **⋯** at the left (Copy path, Show in file manager, Lock… or Unlock, Prune <n> missing), then the last result, the running job with a spinner, or why Open is unavailable, and at the right **New worktree…**, **Remove…** `Del` and the filled primary **Open** `Enter`; on a missing worktree the primary is **Prune <n> missing** (`git worktree prune`, branches kept). Up/Down move the selection, a double click or Enter opens, Esc closes. Open is unavailable, with the reason, for the worktree shown now, a missing folder, a bare repository, and while an operation runs; Remove… keeps the reasons of `can_remove` (main, current, locked, missing, local changes, unreadable status) and never offers a force or delete-files route. **Lock…** asks for an optional reason (`git worktree lock --reason`) and **Unlock** runs `git worktree unlock`; each reports its result in the footer. The window has no Refresh button: it reads the list when it opens, after each change, and whenever Git Good regains focus; until the first list arrives the table stays empty. **New worktree…** asks for the branch first (new, with a start revision, or existing), then the folder, which defaults to a sibling of the repository named `<repo>-<branch>` (slashes become dashes) and follows the branch until edited; **Open after create** (on) switches to the new worktree once it exists. **Remove worktree** says the folder is deleted and the branch stays, with a filled red primary.

Create chooses an exact destination and either an existing local branch or a new branch with a start revision. The destination must be absent or empty, and a branch checked out elsewhere is named with its path instead of being forced. Add runs on a worker, keeps the dialog on failure, and lists the worktree only after Git succeeds. Open saves the current worktree's commit/file selection, filter, reading place, and Local Changes draft before loading the target; each worktree restores its own saved selection and draft, and a new worktree starts empty. Remove re-lists, rechecks dirty/lock/current/main state, confirms the exact path and branch, and runs `git worktree remove` without force. CLI `git good --cli worktree list|add|remove` returns the same inventory and receipts as JSON.

### Submodules

**Repository › Submodules…** (`submodules_view`, also in search) lists every gitlink in the parent index (`gg_git::submodule::list`, read in the background on open and when Git Good gets focus back) as a 22 px table: PATH, STATUS as a pill, RECORDED (the parent index commit), and CHECKED OUT, as 8-character IDs (`—` when not initialized). The footer reads *Recorded = commit staged in the parent index.* with **Open nested repository** and **Details** `Enter`; Up/Down move the selection, Enter or a double click opens the details, and an empty list reads *No submodules in this repository.* Each status has a fixed pill colour: amber for differs (Different commit, Modified), red for broken (Recorded commit missing, Conflict), green for Clean, grey for Uninitialized and Unknown.

A gitlink's **Submodule details…** action is available from the shared reader's File actions menu and from the list. The header reads *Submodule <path>* with the status pill, then one sentence for the status (*The checked-out commit is not the one the parent records.*). A label grid names BEFORE and AFTER (the recorded commits of the comparison, when opened from one), INDEX, and CHECKED OUT as 8-character IDs with their nested subjects, copy buttons for the full IDs, and hints (*same as After*, *same as Before · 14 commits behind After*), then the `.gitmodules` URL and BRANCH; a configured URL difference reads *Local config uses a different URL: <url>*, and any missing `.gitmodules` or status detail follows. The footer's left shows the last result (*Updated vendor/egui to 9b1e6d4c.*) or, when Update is unavailable, the reason in its place (*Stage the parent gitlink before updating: the index records 9b1e6d4c.*, *vendor/egui has local changes. Open it to inspect or clean them.*); its right holds **Open nested repository** and the filled primary (**Update to <id>…**, **Initialize and update…**, or a disabled **Update…**). Historical review keeps Before and After recorded IDs separate from the nested checkout; browsing never initializes, checks out, stages, or fetches a submodule.

Update targets the parent index gitlink and is blocked when the selected recorded commit differs from the index, when the nested tree is dirty, or when the recorded object is missing locally. The confirmation *Check out <id> in <path>?* states that Git may fetch from the URL and that the parent index is not changed, with Cancel `Esc` and **Update** `Enter` side by side. Update runs on a worker, initializes with `git submodule update --init -- <path>`, and rescans the nested and parent status. **Open nested repository** switches to the initialized nested repository as its own context; the parent selection and draft remain in the per-worktree state map. CLI `git good --cli submodule status|update PATH [--repo PATH]` returns the same details and receipt. Network use is explicit in the confirmation; no automatic recursive update, force, or parent staging is added.

### Git LFS

LFS-managed content stays a pointer until an explicit fetch. Pointer detection parses only the canonical v1 header, `oid sha256:` (64 hexadecimal digits), and `size` line, with bounded input and explicit malformed states. **File actions → LFS details…** (`lfs_view`) is headed *LFS <path>* with a status pill (green Object available, red Object missing, amber LFS unavailable). Its label grid shows BEFORE and AFTER as 8-character OIDs with the declared size, *available* or *missing*, and a copy button for the full sha256, then GIT LFS (*available · remote origin* or *not installed*) while the object is missing. A non-pointer file reports that explicitly; pointer text is never presented as the fetched content.

Local Changes uses the same details window with sides taken from the selected area: Staged compares the HEAD entry with the index entry, Unstaged compares the index entry with the bounded working file, and Untracked compares an absent Before with the working file. An unmerged path reports that the conflict must be resolved instead of presenting an index stage as content. Working-file pointer reads stop at 4 KiB and never smudge or materialize content.

When the selected object is present locally, the details window loads a bounded content preview on the worker: objects up to 2 MiB are decoded as PNG/JPEG when possible and otherwise shown as the existing bounded hexadecimal preview, inside a 150 px bordered frame labelled *CONTENT PREVIEW · AFTER* with the dimensions and format (*1600 × 900 PNG*) at the right. Missing, over-budget, unreadable, and non-image content stay explicit. **Export original…** saves the complete original bytes from the LFS store to a new file chosen in the desktop save dialog; the footer's left reports the fetch or export result. Previewing never writes a working file, stages, or imports external content.

**Fetch object…** is enabled only when a target object is missing and `git-lfs` is available; otherwise its reason replaces *Fetching does not change working files.* at the footer's left. The confirmation names the file and size, not the OID (*Download the new version of assets/splash.png?* · *1.4 MiB from origin. Working files are not changed.*), with Cancel `Esc` and **Fetch** `Enter` side by side.

**Repository › LFS…** (also in search) lists the LFS pointers committed in HEAD (`gg_git::lfs::head_pointers`: blobs of at most 1 KiB that parse as canonical pointers, with object availability), filtered by a **Missing <n> | All <n>** switch that starts on Missing. Rows are 22 px: a checkbox (missing objects start checked; available ones cannot be chosen), PATH, the 8-character OBJECT, and SIZE. The footer reads *<n> selected · <size> from <remote>* with **LFS details** for the selected row and the filled primary **Fetch <n> objects** `Ctrl+Enter`, which runs one `git lfs fetch [REMOTE] --include=<paths>` without a further confirmation (each path is one pattern built from its exact bytes, anchored with a leading `/`; `*`, `?`, `[`, `]`, `\` and `#` are escaped; what git-lfs cannot escape matches as `?`: a comma, which splits the list, `!`, `{` and `}`, whose escapes match nothing, trailing whitespace, which it trims, a byte that is not UTF-8, and on Windows every glob character, since git-lfs reads `\` there as a path separator; a `?` can also fetch the objects of paths that differ only there) and reports *Fetched <n> objects (<size>).* An empty view says what fills it (*No LFS pointers in HEAD.*, *No missing objects.*). The list re-reads on open, when Git Good gets focus back, and after a fetch. Fetch runs on a worker with `git lfs fetch [REMOTE] --include=<path>`, then rescans object availability; no automatic network, smudge, materialization, staging, or working-tree write is added. CLI `git good --cli lfs status|fetch PATH [--area staged|unstaged|untracked|conflict] [--revision REF] [--before REF] [--repo PATH]` returns the same details and receipt for review-time or Local Changes pointers. Smudging/materializing fetched content into working files remains planned and must stay an explicit action.

### Signing

**Verification.** Commit details exposes **Signature details…**, and a tag's ref menu exposes the same action. The window (`signature_view`) is titled by the object (*Signature · commit 6b14dc55*, *Signature · tag v0.4.0*) and shows the result as a coloured banner with an icon: green Good signature, red Bad signature and Verification error, amber Unknown key (signed but untrusted), grey Unsigned and Verification unavailable, and a grey *Verifying signature…* banner of the same height while Git runs. Below it a label grid lists only the rows Git reported (SIGNER, KEY with a copy button, TRUST, FORMAT); the footer reads *Read-only check; nothing is changed.* with **Signing settings…**, which opens Preferences › Commit. The window and CLI resolve the object type and run `git verify-commit --raw` or `git verify-tag --raw` through the repository's configured signing tool. Git's raw status is parsed into separate fields: unsigned, good, bad, unknown key, verification unavailable, or error; signer identity, key fingerprint/ID, trust label, declared format, and the underlying detail. An unsigned object is not an empty success, an unknown public key is not a bad signature, and a valid signature is reported separately from its trust. Verification is read-only: it never imports keys, changes trust stores, or writes repository signing configuration. `git good --cli signature config|verify [REF] [--repo PATH]` returns the same configuration and verification as JSON.

**Configuration.** The signer reads `gpg.format` (default `openpgp`), `user.signingkey`, `gpg.program`, `commit.gpgsign`, `tag.gpgsign`, and `gpg.ssh.allowedSignersFile` through normal Git configuration inheritance, and reports whether the configured signing tool is available. The application never writes these keys. The configuration is shown once, in Preferences › Commit under the signing choices, as read-only rows read in the background when Preferences opens (Format · `gpg.format`, Signing key · `user.signingkey`, Allowed signers · `gpg.ssh.allowedSignersFile`) with *Read from Git config.* and **Edit in repository config…**, which opens the repository's config file in the configured editor. Validity and trust stay separate facts in Signature details.

**Signed commits.** Local Changes shows a **Sign** choice next to Amend in wide windows (narrow ones follow Preferences › Commit), initialized from `commit.gpgsign`; it is enabled only when a signing key is configured and the tool is available. The choice is captured with the draft, so view and repository switches do not silently change it. When signing is requested, the commit worker runs the normal pre-commit/prepare-commit-msg/commit-msg hooks, then asks `git commit-tree -S` to sign the observed tree, parents, message, and pinned author/committer identities. Only after signing succeeds does the app update `HEAD` under the reference lock and run post-commit/post-rewrite. A missing key, unavailable tool, or agent failure aborts before any reference update and keeps the message, index, and working tree; there is no unsigned fallback. The status line names a signed commit, and CLI `git good --cli commit --sign` follows the same contract. Without an explicit flag, the CLI follows `commit.gpgsign`; `--no-sign` is an explicit opt-out.

**Signed tags.** **Branch → New tag…** is available from the Branch menu and search at every width. The dialog requires a name, explicit target (the selected commit or `HEAD`), and annotated message. **Sign tag** is initialized from `tag.gpgsign` and disabled with a reason when the key or tool is unavailable. Creation runs `git tag -s` (or `git tag -a` when unsigned) on a worker; failure leaves no tag and keeps the dialog fields, while success refreshes refs. CLI `git good --cli tag --create TAG --at REF -m MESSAGE [--sign|--no-sign] [--repo PATH]` returns a receipt with the tag, target, object ID, and signed state; tag signature verification uses the same Signature details or `git good --cli signature verify`.

### Deferred large-repository features

Materializing or smudging fetched Git LFS objects into working-tree files and image blend modes beyond normal-alpha onion skin (such as difference heatmaps) remain planned follow-ups. Neither is represented by a placeholder control.

## Repository and decision dialogs

**Repository › Open…** (`Ctrl+O`) opens a modal: a folder field with **Browse…**, up to ten recent repositories (the one limit shared with the welcome view and Open recent) filtered by what is typed (folder name, then the path dimmed), **Clone…** to switch to the Clone dialog, **Cancel** (`Esc`), and **Open** (`Enter`). **Repository › Open recent** lists the folder name first and the path after it, checks the open repository, keeps a missing folder listed but disabled (*Not found*), and ends with **Clear recent**. **Repository › New repository…** (also a welcome card, **Initialize here…**, and a search action) opens the modal *New repository*: **Folder** (path field with **Choose…**), **First branch** (`main`), **Commit the existing files as “Initial commit”** (checked), and one reserved weak line read in the background: `<folder> has 14 files (3 ignored by .gitignore).`, `<folder> is empty.`, or `<folder> will be created.`; when the folder is inside a repository it reads `<folder> is inside the repository <repo>. Open it instead?` with **Open <repo>**, and the primary stays disabled. The footer has **Cancel** (`Esc`) and the filled **Create repository** (`Enter`). `gg_git::init::init` runs off the UI thread: it refuses inside a repository, creates the folder when missing, runs `git init -b <branch>`, and optionally `git add -A` and `git commit -m "Initial commit"`; the new repository then opens and joins the recent list, in History when it committed and in Local Changes otherwise. Recent repositories are stored in `settings.json` as `recent_repositories` entries `{"path", "opened"}` (seconds since the Unix epoch); plain path strings from older versions still load. **About Git Good** offers **Copy version info** (Git Good, OS and architecture, and `git --version`) and **Close**.

Destructive confirmations list what they remove before their filled red primary names the count. The list is read with Git on a background thread when the dialog opens, in a fixed-height slot that stays empty until it arrives, and the primary is enabled once it has: **Changes → Discard all tracked changes…** (dialog *Discard all tracked changes*: every tracked file to HEAD, staged and unstaged changes both lost, untracked files kept, files only added to the index left untracked) lists the tracked files restored to HEAD (`Discard 4 files, staged and unstaged`); **Reset here** lists the commits that leave the branch and, for a hard reset, the changes lost and, under `UNTRACKED FILES OVERWRITTEN`, the untracked or ignored working files whose paths the target tracks (`Hard reset`); while that list is not empty the primary stays disabled and the dialog reads *Move or delete the untracked files listed above, then reset.*, and `gg_git::reset::reset` refuses such a hard reset itself, listing the paths with nothing changed (it compares the paths as the bytes Git prints, so a name that is not UTF-8 or a working tree whose folder ends with a space is still found on disk), and saves the tip it leaves as a `reset` backup before every Soft, Mixed or Hard reset, failing with nothing changed when it cannot, while the status line names that backup; **Delete branch** lists the commits not in the current branch, and its one button deletes a merged branch or force-deletes an unmerged one (`Delete keep and 2 unmerged commits`). Each of these dialogs also records HEAD and its target (`rev-parse`) with its lists. Confirming reads all of them again on a background thread, the primary disabled meanwhile: when every read matches what the dialog showed, the action runs; otherwise nothing runs, the lists update in place, and a reserved row above the footer reads *The repository changed; review the updated list and confirm again.* Delete on origin needs no re-read because the push names the last fetched commit as its lease.
